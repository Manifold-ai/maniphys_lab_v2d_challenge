Tier 2 denoising

Tier 2 noise is a capped random walk that starts at zero (caps of about 30° and 30 mm). Inside a static segment, every observed increment is a drift increment, and every version from v1 on builds on that fact. The chart shows ADD-AUC of each version against the Tier 1 ground truth.

Reading the chart

The dashed bars, v5.2 and v5.3, use parameters derived from Tier 1, so their compliance is doubtful; they are shown for reference only. The green bar, v5.4, is the submission version: every parameter comes from Tier 2 alone, at a cost of −0.041. See ADR-00002.

How the guard works

libs/v2d_infra/tier_guard.py is called when a submission-pipeline process starts. It intercepts five read paths (open, np.load, pq.read_table, pq.ParquetFile, glob) and raises on any read of the Tier 1 folder. Re-exporting v5.3 under the guard matched the previous output bit for bit on 30 of 30 sequences, which shows the export never reads Tier 1.

已知风险

  • 构建走不走镜像源：BuildKit 的 FROM 是否经 daemon 的 registry-mirrors 拉取，未核实。若 diff_id 对不上或拉取失败，先停下回报，不改 base。
  • 共享卡：JAX 的显存上限按整卡算，别人中途占卡，先被挤掉的是 Warp 那部分，可能跑了几小时才 OOM。9/28 起两台卡只有 rxzhou 在用；训练链开跑与每条 run 前查卡，有别人的进程就停。
  • 回放速度：kit 按源帧逐帧计分，训练固定用逐帧（见官方评测与提交）。“真实时长训练的 policy 会被错位计分”是读代码推出的（jev 0.16，未核实），没在新评测器上实测；接上 aee95f2 后用 ep20 验一次。
  • 陷桌面：Tier 2 的熨斗、电饭煲陷进桌面约 2 cm，观察这两条的终止原因是否集中在物体。
  • 官方 1 个世界评测：我们一直按 4096 世界的均值判，官方每条只评 1 个世界、确定性动作，单个世界的结果可能和均值差很多。接上 aee95f2 后先在已评过的 policy 上对比。
  • mf4090 磁盘：9/29 傍晚剩 13 GB；fc_run.sh 只留最近 2 份 state，一条满配约 0.5 GB、冒烟约 0.16 GB，第 1 批剩下的放得下。回传前先清理不再需要的冒烟产物。
  • 100 万 buffer：Day 1 里那条从课程第 0 阶段起就明显更差（chord_sr 0.017 vs 0.79，单种子）（两条同时换了 GPU 与机器，差别不能单独归因于 buffer）。4090 放不下默认的 1000 万；400 万跑逐帧可用（ep27 过线），跑真实时长不可用（Day 2 Q3）。
  • 选序列：起步序列按平移挑的，ep20 物体只平移 4 cm，却要原地转近一圈。按物体位移和在动帧排难度会漏掉旋转；Day 2 改为按帧数分档机械挑选，并要求支撑面类型不全相同。
  • 判据与参数不一致：9/28 mf4090 开链时给的显存上限（23000 MiB）没写进计划，与登记的判据（只看 OOM 字样）不一致，三条冒烟被误判跳过。开链参数要从登记的判据推出来，开链前逐项对一遍。
  • 评测器遇到发散世界直接报错：ep7 的冒烟 policy 就是这样，256 个世界里 172 个发散（见第 1 批批量）。官方每条只评 1 个世界，训好的 policy 在那个世界里若发散，这条交不出轨迹，而每次提交要有全部 30 条。批量后复现，必要时问组委会。
  • 时长随序列变：ep1 比同机的 ep6 慢近一倍，冒烟看不出来；出分时间报区间，不按单条均值排。

Known risks

  • Build mirror path: whether BuildKit's FROM pulls through the daemon's registry-mirrors is unverified. If the diff_ids do not match or the pull fails, stop and report instead of changing the base.
  • Shared card: JAX sizes its memory limit from the whole card, so if someone takes the card mid-run, Warp's share is squeezed first and the run can fail hours in. Since 9/28 rxzhou is the only one using either card; training chains check the card when they start and before every run, and stop if another user's process is there.
  • Playback speed: the kit scores frame by frame against the source frames, and training uses frame-by-frame playback only (see Official evaluation and submission). That a real-time-trained policy would be scored out of step was inferred from the code (jev 0.16, unverified) and has not been tested on the new evaluator; check it once on ep20 after the aee95f2 evaluator is in place.
  • Tabletop sinking: the Tier 2 iron and rice cooker sink about 2 cm into the tabletop; watch whether their termination causes concentrate on the object.
  • One-world official evaluation: we have always judged by the mean over 4096 worlds, while the organizers evaluate one world per episode with deterministic actions, and a single world can land far from the mean. Once aee95f2 is in place, compare the two on policies we have already evaluated.
  • mf4090 disk: 13 GB left on the evening of 9/29; fc_run.sh keeps only the latest 2 states, about 0.5 GB per full run and 0.16 GB per smoke, so the rest of batch 1 fits. Clear smoke outputs that are no longer needed before syncing checkpoints back.
  • 1M buffer: on Day 1 that run was clearly worse from curriculum stage 0 on (chord_sr 0.017 versus 0.79, single seed) (the two runs also differ in GPU and machine, so the gap is not attributable to the buffer alone). The 4090 cannot hold the default 10M; 4M works for frame playback (ep27 passes) but not for real-time playback (Day 2 Q3).
  • Sequence choice: the starting sequences were picked by translation; ep20 moves the object only 4 cm but turns it in place almost a full circle. Ranking difficulty by displacement and moving frames misses rotation; Day 2 instead picks mechanically by length tiers and requires mixed support types.
  • Criteria versus parameters: on 9/28 the memory limit given when launching the mf4090 chain (23000 MiB) was not in the plan and disagreed with the registered criterion (OOM messages only), so three good smokes were skipped. Launch parameters must follow from the registered criteria; check them item by item before launching.
  • The evaluator errors out on a blow-up: that is what happened with the ep7 smoke policy, with 172 of 256 worlds blowing up (see Batch 1). The organizers evaluate one world per episode; if a trained policy blows up in that world, the episode yields no trajectory, and every submission needs all 30. Reproduce after the batch and ask the organizers if needed.
  • Run time depends on the sequence: ep1 took nearly twice as long as ep6 on the same machine, and the smoke gave no hint; report expected results as ranges instead of planning with a single mean.
