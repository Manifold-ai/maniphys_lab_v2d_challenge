Tier 2 denoising

Tier 2 noise is a capped random walk that starts at zero (caps of about 30° and 30 mm). Inside a static segment, every observed increment is a drift increment, and every version from v1 on builds on that fact. The chart shows ADD-AUC of each version against the Tier 1 ground truth.

Reading the chart

The dashed bars, v5.2 and v5.3, use parameters derived from Tier 1, so their compliance is doubtful; they are shown for reference only. The green bar, v5.4, is the submission version: every parameter comes from Tier 2 alone, at a cost of −0.041. See ADR-00002.

  1. Convert: challenge_to_soma.py turns a challenge parquet into the input folder of the official retargeter. The body keeps its per-frame bone-length parameters; dropping them shifts every joint by 13.5 mm.
  2. Denoise Tier 2: export_tier2.py v5.4 blocks all Tier 1 reads as soon as the process starts, and writes one pose file per sequence.
  3. Retarget and check alignment: batch.sh runs the official soma_to_g1 in a throwaway container, then measures the gap between the object and the floor or tabletop.
  4. Train: fc_train.sh, FlashCHORD G1 FlashSAC, 350 million environment steps per full run. The default replay buffer size is 10 million, which needs a 48 GB GPU.
  5. Evaluate: evaluate_policy.py reports ADD-AUC, MPPE and success rates. The success-rate fields in the evaluation JSON are spider_sr_uncentered, maniptrans_sr and chord_sr; judging by the names, the first two correspond to SP-SR and MP-SR, which has not been checked against the official evaluation. It compares against the policy's own reference, so an offline evaluation against ground truth is still needed (see next steps).
  6. Submit: the organizers require eval_robotic_grounding.py, which is not released. Up to 5 submissions per week, unlimited in the final three days.

How the guard works

libs/v2d_infra/tier_guard.py is called when a submission-pipeline process starts. It intercepts five read paths (open, np.load, pq.read_table, pq.ParquetFile, glob) and raises on any read of the Tier 1 folder. Re-exporting v5.3 under the guard matched the previous output bit for bit on 30 of 30 sequences, which shows the export never reads Tier 1.

Multiple training machines (added 9/26)
  • .env holds shared variables and credentials; .env.<name> overrides only the host and path and is selected with V2D_ENV=<name>. A misspelled name stops with an error instead of falling back to the default host, because the sync uses --delete.
  • Pull-backs land in per-host folders, runs/<host>/ and results/<host>/; only policies and logs come back, never state files.

批量训练

  • 单卡顺序排队：先 Tier 1 30 条，再 Tier 2 30 条；每条一个输出目录 runs/flash_chord/t{档}_ep{序号}_…/。
  • 每次运行落盘一份记录：仓库 commit、上游 commit、镜像 ID 与 base 层、parquet 的 sha256、完整配置（--cfg job --resolve 的输出）、seed、GPU 型号、开始与结束时间、评测 JSON。
  • 每份 checkpoint 约 165 MB（policy 4.9 MB + state 160 MB），一次全程存 35 份约 5.8 GB。训练完用 V2D_ENV=ml40 scripts/dev/pull-runs <run> 把 policy 和日志拉回本地；state 只用于续训，留在训练机上，批量时只留最后 2 份。
  • 不做跨档热启动：Tier 2 的策略从头训练，理由见 ADR-00002。

Batch training

  • One card, one queue: the 30 Tier 1 sequences first, then the 30 Tier 2 sequences; one output folder per run, runs/flash_chord/t{tier}_ep{id}_…/.
  • Every run writes a record: repository commit, upstream commit, image ID and base layers, parquet sha256, full config (output of --cfg job --resolve), seed, GPU model, start and end time, evaluation JSON.
  • Each checkpoint is about 165 MB (policy 4.9 MB + state 160 MB), and a full run saves 35 of them, about 5.8 GB. After training, V2D_ENV=ml40 scripts/dev/pull-runs <run> brings the policies and logs back; state files are only for resuming, stay on the training machine, and only the last 2 are kept during the batch.
  • No cross-tier warm start: Tier 2 policies train from scratch, as ADR-00002 explains.

已知风险

  • 构建走不走镜像源：BuildKit 的 FROM 是否经 daemon 的 registry-mirrors 拉取，未核实。若 diff_id 对不上或拉取失败，先停下回报，不改 base。
  • 共享卡：JAX 的显存上限按整卡算，别人中途占卡，先被挤掉的是 Warp 那部分，可能跑了几小时才 OOM。时段约定要写清起止。
  • 播放速度：FlashCHORD 默认 1.67 倍速，官方口径未知（见 ADR-00001）；Day 1 之后抽一条训练真实时长版本对比。
  • 陷桌面：Tier 2 的熨斗、电饭煲陷进桌面约 2 cm，观察这两条的终止原因是否集中在物体。
  • 官方评测：eval_robotic_grounding.py 发布当天，用它重评已有 checkpoint，核对本地指标。
  • mf4090 磁盘：只剩约 20 GB，checkpoint 回传前先清理不再需要的冒烟产物。
  • 100 万 buffer：Day 1 里它从课程第 0 阶段起就明显更差（chord_sr 0.017 vs 0.79，单种子）。4090 放不下默认的 1000 万，mf4090 上的 FlashCHORD 训练不用来比较配方。
  • 选序列：起步序列按平移挑的，ep20 物体只平移 4 cm，却要原地转近一圈。按物体位移和在动帧排难度会漏掉旋转，后续挑序列要同时看累计转角。

Known risks

  • Build mirror path: whether BuildKit's FROM pulls through the daemon's registry-mirrors is unverified. If the diff_ids do not match or the pull fails, stop and report instead of changing the base.
  • Shared card: JAX sizes its memory limit from the whole card, so if someone takes the card mid-run, Warp's share is squeezed first and the run can fail hours in. Agree on explicit start and end times.
  • Playback speed: FlashCHORD plays at 1.67× by default and the official setting is unknown (see ADR-00001); after Day 1, train one sequence at real time as well and compare.
  • Tabletop sinking: the Tier 2 iron and rice cooker sink about 2 cm into the tabletop; watch whether their termination causes concentrate on the object.
  • Official evaluation: on the day eval_robotic_grounding.py is released, re-evaluate existing checkpoints with it and reconcile the local metrics.
  • mf4090 disk: about 20 GB left; clear smoke-run outputs that are no longer needed before syncing checkpoints back.
  • 1M buffer: on Day 1 it was clearly worse from curriculum stage 0 on (chord_sr 0.017 versus 0.79, single seed). The 4090 cannot hold the default 10M, so FlashCHORD training on mf4090 is not used to compare recipes.
  • Sequence choice: the starting sequences were picked by translation; ep20 moves the object only 4 cm but turns it in place almost a full circle. Ranking difficulty by object displacement and moving frames misses rotation, so future picks should also look at the total rotation.
