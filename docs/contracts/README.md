# 契约

功能由契约定义，不由实现定义。一份契约一个契约面：`docs/contracts/<面>.md`，边界写在
文件抬头。项目还没建的，契约先写着。

## 一条契约长什么样

每份契约文件是四张表，对应四层，每行一条契约条目：

| ID | 主题 | 交付 | 验证 | 审阅 | 状态 |
|---|---|---|---|---|---|
| DATA-I001 | 档位隔离 | （示例）Tier 2 / 3 的读取入口拒绝打开 Tier 1 目录 | `libs/v2d_infra/tests/test_tier_isolation.py`<br>- test_a | 待审 | 草案 |

- **ID**：`<面缩写>-<层><序号>`，层用 `U`（User-facing）/ `C`（Caller）/ `D`（Data）/
  `I`（Internal）。一旦分配就不改也不复用，不再成立的条目标 `已废弃` 留在表里。
- **主题**：可选的分组标签，同主题的条目相邻排列。
- **交付**：上线后什么会成真，一句话、可判定真假。「效果好」不是交付，「Tier 1 本地
  复算 MPPE 与官方脚本输出之差在 1e-6 以内」是。
- **验证**：文件路径加逐行测试名，单元格内用 `<br>` 分行。人工验证写成
  `人工：<步骤>｜验证域：<路径>`。
- **审阅**：`待审` / `已确认`。**推进到已确认只能由人做**；契约文字或它的测试一旦改动，
  改动方负责退回待审。
- **状态**：`草案` → `已实现` → `已验证`；另有 `未实现`、`不适用`、`已取代`、`已废弃`。
  状态为 `已验证` 时验证列必须有可解析的引用。

审阅与状态两列正交：测试通过只证明代码符合写它的人的意图，不证明那个意图是对的。

## 规则

- 没有验证就不是契约，是愿望。要么让它可观测，要么写下人工验证步骤，要么砍掉。
- 每个测试在 docstring 里标注它守的契约 ID，指不回就删掉这个测试。
- 一条契约只讲一件可判定的事。
- 非目标显式写在契约文件末尾。
- 契约门禁（`tools/contract_review`）尚未建立，在它落地之前上面几条靠人工核对。

## 四层是什么

| 层 | 管什么 |
|---|---|
| **User-facing** | 使用者（人或 agent）能观察到的输入输出、失败模式、边界情况 |
| **Caller** | 对外的程序接口：命令、函数签名与语义、错误分类 |
| **Data** | 落盘与交接的 schema、坐标系、帧号、不变量 |
| **Internal** | 组件间的顺序与生命周期假设、资源归属 |
