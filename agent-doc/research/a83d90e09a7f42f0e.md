# PAPER A — DexMachina (arXiv 2505.24853)

**Title/venue**: "DexMachina: Functional Retargeting for Bimanual Dexterous Manipulation", Zhao Mandi, Yifan Hou, Dieter Fox, Yashraj Narang, Ajay Mandlekar\*, Shuran Song\* (\*equal advising). arXiv v1, 30 May 2025, cs.RO/cs.AI/cs.LG, license CC BY 4.0 ([abs](https://arxiv.org/abs/2505.24853), [html v1](https://arxiv.org/html/2505.24853v1)). Only **v1** exists on arXiv. Listed as an **ICML 2026 poster** ([icml.cc/virtual/2026/poster/63277](https://icml.cc/virtual/2026/poster/63277)); OpenReview record at [openreview.net/forum?id=3c6bnSJwDg](https://openreview.net/forum?id=3c6bnSJwDg) (behind Cloudflare, could not read the decision text). Project page: [project-dexmachina.github.io](https://project-dexmachina.github.io/). Docs: [mandizhao.github.io/dexmachina-docs](https://mandizhao.github.io/dexmachina-docs).

## 1. Core idea

"Functional retargeting": given one ARCTIC human hand–object demo `D^η = {G, H}` (T timesteps of dense object states + MANO hand poses) and a pair of dexterous robot hands ζ, learn `π_θ^{η,ζ} = argmin_θ Σ_t F(ĝ_t, g_t)` — i.e. track *object* states (position, rotation, articulation angle), not hand poses. Three ingredients: (a) a product-form object-tracking task reward; (b) a **hybrid action space** — kinematic-retargeting joint values are base actions for the 6-DoF wrist with a policy residual on top, fingers use absolute normalized targets — plus motion-imitation / behavior-cloning / contact auxiliary rewards derived from the demo; (c) the headline contribution, an **auto-curriculum with virtual object controllers**: the object gets 7 virtual PD-actuated DoFs (6 base + 1 articulation) that drag it along the demo trajectory, and the gains `(k_p, k_v)` are exponentially decayed whenever *all four* reward-term running means exceed thresholds, handing control over to the policy. (§3, §4, §4.3 of the [HTML](https://arxiv.org/html/2505.24853v1))

## 2. Observation representation

Paper (Appendix B.2) is one sentence: *"We use state-based input for policy observation space: this include object states, joint targets, finger-to-object distances, and normalized hand-object contact forces."* Exact composition comes from the code.

Per-hand robot block — [`dexmachina/envs/robot.py::compute_obs_dim` / `get_observations`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/envs/robot.py):
```python
dims = dict(qpos_dim=self.ndof, qpos_target_dim=self.ndof, qvel_dim=self.ndof,
            kpt_dim=int(len(self.kpt_link_names)*3), wrist_dim=7)
```
- `dof_target_pos` = `curr_targets - dof_pos` (ndof)
- `dof_pos` unscaled to `[-1,1]` by joint limits (ndof)
- `dof_vel` (ndof)
- `kpt_pos` flattened, n_kpts × 3 (keypoint links = configured tip links **+ all collision links**, or overridden by the saved retargeting `kpts_data`)
- `wrist_pose` 7 (pos + quat)

Note `self.ndof = len(actuated_joints)` **includes mimic joints**, so it is ≥ action dim.

Object block — [`envs/object.py::compute_obs_dim`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/envs/object.py):
```python
dims = dict(parts_pose_dim=7*self.n_links, root_ang_vel_dim=3, root_lin_vel_dim=3,
            dof_pos_dim=self.num_joints, state_diff_dim=8)
```
For ARCTIC articulated objects `n_links = 2` (`bottom`, `top`), `num_joints = 1` → **29 dims**. `state_diff` (8) = `demo_state[t+goal] − [root_pos(3), root_quat(4), joint_qpos(1)]`.

Global extras ([`envs/base_env.py::get_observations`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/envs/base_env.py)):
- normalized episode phase: `2·episode_length_buf/max_episode_length − 1` (1 dim) — always on
- `observe_tip_dist` (`-obt`): closest-vertex distance from each hand keypoint to each of the 2 object parts, for both hands → `n_kpts × 2 × 2`
- `observe_contact_force` (`-obf`): `‖contact_forces‖ × 0.01` over `num_obj_links × num_robot_links` pairs
- Final obs clipped to ±5.0 (`obs_clip`), NaNs replaced by `−obs_clip`

**No future reference window** — the policy sees only the current target implicitly via `state_diff` and the episode phase. **No asymmetric actor-critic**: the wrapper returns `dict(policy=obs, itemized=..., critic=obs)` — critic and actor get identical inputs; `num_privileged_obs = None`. The "privileged" information in this paper refers to the virtual object controllers, not to a critic-only observation.

## 3. Action space

Bimanual, single policy: `action_dim = action_dim_left + action_dim_right`, per hand = #actuated joints − #mimic joints. Actions clipped to `[-1, 1]` (`action_clip=1.0`, `action_scale=1.0`).

Paper's hybrid formulation (Appendix A.3, verbatim):
```
a_t^{wrist-T} = a_t[I_w^T] ∈ R^3,  q_t^{wrist-T} = q_t[I_w^T] + s_T · a_t^{wrist-T}
a_t^{wrist-R} = a_t[I_w^R] ∈ R^3,  q_t^{wrist-R} = q_t[I_w^R] + s_R · a_t^{wrist-R}
a_t^{fingers} = a_t[I_f],          q_t^{fingers} = ℓ_{I_f} + ((u[I_f] − ℓ[I_f])/2)·(a_t^{fingers} + 1)
q̂_t = concat(q_t^{wrist-T}, q_t^{wrist-R}, q_t^{fingers})
```
where `q_t` are the collision-aware kinematic-retargeted joint values.

Code ([`robot.py::translate_actions`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/envs/robot.py)) confirms, and gives scales: `hybrid_scales = (s_T, s_R)`, default `(0.04, 0.5)` (comment: *"from objdex paper: wrist delta actions ±4 centimeters for transition and ±0.5 radian for rotation"*); the released paper-config script uses `--hybrid_scales 0.1 1.0` (±10 cm, ±1 rad), and the eval grouping config confirms the paper runs used `hybrid_scales: [0.1, 1]`. Other modes exist for ablations: `absolute`, `residual` (residual on *all* joints, scaled by margin to limits), `relative`, `kinematic` (open-loop replay). Targets then pass through mimic-joint multipliers, are clamped to limits, and go through an EMA `action_moving_avg` (default 1.0 = no smoothing).

Control is **joint position targets for Genesis PD controllers**, not torques. Per-group gains, e.g. Inspire: fingers `kp=20, kv=1, force_range=50`; wrist rotation `kp=80, kv=5`; (a hardcoded tuned variant uses wrist `kp=300, kv=30`, fingers `kp=20, kv=2`).

**Control frequency**: `dt = 1/60 s` with `substeps=2` → 60 Hz control, 120 Hz physics substepping, **decimation = 1** (one `scene.step()` per policy action — see `base_env.py::step`).

## 4. Rewards

**Task reward** (§4.1, verbatim):
```
d_pos = ||ĝ_t^T − g_t^T||_2 ;  d_rot = 2 cos^{-1}(|⟨ĝ_t^R, g_t^R⟩|) ;  d_ang = ||ĝ_t^J − g_t^J||_2
r_task = r_pos * r_rot * r_angle = exp(−β_pos d_pos) exp(−β_rot d_rot) exp(−β_ang d_ang)
```
Multiplicative (not additive) "encouraging balanced learning". Code: `arti_dist = (obj_arti − demo_arti)²/2`; betas from `--task_rew_betas` → `(obj_pos_beta, obj_rot_beta, obj_arti_beta)`; released script uses **`10, 1, 5`**; `get_reward_cfg` defaults are `20, 5, 20`; ObjDex-baseline mode forces `30, 2, 10` (and in `rewards.py` `objdex_baseline` also sets `obj_pos_beta=1, obj_rot_beta=20, obj_arti_beta=5`, zeroing all aux weights). There's also an unmentioned `well_track` bonus flag: `(pos_dist<0.005) & (rot_dist<0.1) & (arti_dist<0.1) & (demo_arti>0.1)`, scaled by `scale_well_track` (default 1.0 = off).

**Motion-imitation + BC rewards** (§4.2, verbatim):
```
r_imi = (1/K) Σ_{i=1..K} exp(−β_imi ||x̂_i − x_i||_2) ;  r_bc = (1/J) Σ_{i=1..J} exp(−β_bc ||q̂_i − q_i||_2)
```
⚠️ **Paper/code discrepancy**: the default code path (`exp_kpt_first=False`) computes `exp(−β · mean_i dist_i)` — exp of the mean, not mean of exps. Also the code blends a wrist term the paper's formula omits: `r_imi = λ_imi · [w_wrist · r_wrist + (1 − w_wrist) · r_fingertip]`, with `imi_wrist_weight` = 0.5 in the released script, `imi_wrist_pos_beta=10`, `imi_wrist_rot_beta=3`, `imi_fingertip_beta=20`, `bc_beta=500`.

**Contact reward** (§4.2, verbatim, Eq. 1–2):
```
D = ||C − Ĉ||_2 ∈ R^{N×K};  set D^{(i,j)} = { d_max  if M_demo^{(i,j)} ≠ M_policy^{(i,j)}
                                            { 0      if M_demo^{(i,j)} = M_policy^{(i,j)} = 0
r_con = (1/(2NK)) ( Σ_i Σ_j exp(−β_con D_left^{(i,j)}) + Σ_i Σ_j exp(−β_con D_right^{(i,j)}) )
```
`contact_beta` default 30, released script uses 10; alternative sigmoid form with `contact_a=100, contact_b=5`.

**Total**: `r_t = λ_task r_task + λ_imi r_imi + λ_bc r_bc + λ_con r_con`. Released script: `λ_task = 1.0` (default `task_rew_weight`), `-imi 0.3 -bc 0.3 -con 3`. (The eval grouping config shows paper runs also used `imi_rew_weight` 0.2 or 0.3 and `contact_rew_weight` 2 or 3.)

**Two penalty terms the paper does not mention** ([`rewards.py::compute_reward`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/envs/rewards.py)):
- force penalty (default weight 0.1): `mean(max(‖F‖ − 500, 0))` over all contact pairs
- action penalty: `mean(a²) × action_penalty`, `0.01` in the released script

**Curriculum (Algorithm 1)** — per PPO iteration, for each finished episode compute `r̄_z = R_z / L_max` for `z ∈ {task, imi, bc, con}`, push onto a deque, take deque means `μ_z`; if `μ_z > σ_z ∀z` then `k_p ← k_p·φ_p`, `k_v ← k_v·φ_v`, and if `k_p ≤ 0.01` set `k_p, k_v ← 0`. Released config: `--kp_init 80 --kv_init 5 --curr_rew_thres 0.6 0.01 0.01 0.01` (σ_task=0.6, σ_imi=σ_bc=σ_con=0.01), `--deque_len 30`, `--wait_epochs 100`, `--curr_schedule uniform --gain_mode all --uniform_mode slow`, `--upper_ratios 0.9 0.9 1 --lower_ratios 0.8 0.8 1` (kp, kv, force_range). Object controller defaults in `object.py`: `kp=1000, kv=100, force_range=200`; curriculum defaults `kp_init=1000, kv_init=10`, `rew_thresholds = dict(task=0.5, con=0.05, imi=0.05, bc=0.05)`, `dialback_ratios = 0.98` for all three. `object.py::step` drives `entity.control_dofs_position(demo_dofs[t+1])` over `dof_idxs = list(range(7))` — confirming **6 base + 1 articulation virtual DoFs**.

**Early termination** (`base_env.py::_get_dones`): timeout; NaN; object root `z < table_height`; and a cumulative-reward gate — every `early_reset_interval=5` steps, reset if `cumulative_task_rew < early_reset_threshold × elapsed` (`-ert 0.6` in the released script). Optional per-aux-term gates (`--aux_reset_thres 0 0 0`, i.e. off).

**ManipTrans-baseline curriculum reimplementation** (§B.3, verbatim): decays `ε_object^P, ε_object^R, ε_finger, g_gravity, μ` with `ω_current = ω_init · (ω_final/ω_init)^{t/I}`, ranges `g_gravity ∈ [0, −9.81]`, `μ ∈ [4.0, 1.0]`; note "ManipTrans does not disclose the exact decaying schedule … or the range for gravity and friction parameters". Implemented in [`envs/maniptrans_curr.py`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/envs/maniptrans_curr.py).

## 10. Metrics

**§B.4, verbatim on why**: *"prior work has explored per-step success rate [ObjDex] or tracking error [ManipTrans], but both have clear shortcomings: success rate reporting is based on how many timesteps out of the entire demonstration a policy can move the object to track within given error thresholds, hence the results are highly sensitive to the threshold values (this case requires 3 different thresholds for position, rotation, and joint angle errors), which also depend on the object size and geometries."*

Their metric: **ADD-AUC**. Footnote, verbatim: *"ADD stands for Average Distance, AUC stands for Area Under Curve, we don't use ADD-S because we have the exact matching targets from the demonstration metric with the key difference that we compute ADD for each object part separately (to accommodate articulated objects) and average ADD results before computing AUC."*

Exact definition from [`eval/eval.md`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/eval/eval.md), verbatim:
> ADD (Average 3D Distance) metric: for each eval env and each part (`top`, `bottom`), transform a fixed set of sampled mesh vertices into world space for both `demo_state` and `obj_state`, compute per-vertex L2 distances, average over vertices to get per-frame distances, then store as `add.npy` with shape `(num_eval_envs, num_frames)` per part.
> AUC (Area Under the Curve): for each part, compute accuracy at thresholds `[0.01, 0.02, ..., 0.09]` as `mean(add < thres)`; then compute trapezoidal AUC over normalized x-values `linspace(0, 1, len(thresholds))`; final AUC is the mean over parts.

Code ([`eval/compute_add.py`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/eval/compute_add.py)):
```python
thresholds = list(np.arange(0.01, 0.1, 0.01))          # 1cm … 9cm, 9 values
def compute_auc(mean_add, thresholds):
    accuracies = [np.mean(mean_add < thres) for thres in thresholds]
    x_values = np.linspace(0, 1, len(thresholds))
    return float(np.trapz(accuracies, x=x_values))
```
`num_samples = 500` vertices per part; object loaded with `convexify=True`, `disable_collision=True`, `gravity=(0,0,0)`.

⚠️ **Paper/code discrepancy**: the paper says ADD is averaged across parts *before* AUC; the code computes AUC per part and averages the **AUCs** (`auc["overall"] = mean(list(auc.values()))`).

**Eval protocol** (§B.4, verbatim): *"For each method and task, we run 5 random seeds; each seed run saves a best policy checkpoint based on cumulative task reward, and each checkpoint is evaluated for 20 episodes."* The y-axis labelled "success rate" in Fig. 3 / Fig. 5 is this ADD-AUC value.

**Tasks** (7 ARCTIC clips, exact strings from [`eval/group_cfgs/dexmachina_main.yaml`](https://github.com/MandiZhao/dexmachina/blob/main/dexmachina/eval/group_cfgs/dexmachina_main.yaml)): short-horizon `ketchup30-130-s01-u01`, `box30-230-s01-u01`, `mixer30-200-s01-u01`; long-horizon `ketchup40-340-s01-u02`, `mixer40-340-s01-u01`, `notebook40-340-s02-u02`, `waffleiron40-340-s01-u01`. 5 articulated objects.

**Numbers actually quoted in prose** (§B.3): their ObjDex reimplementation gets *">90% success rate for all hands"* on Ketchup-100 (original paper: 41.2%) and *">70% for three out of four hands"* on Mixer-170 (original: 57.6%). Fig. 3/5 bar values are not in the HTML text.

# PAPER B — ManipTrans (arXiv 2503.21860)

**Title/venue**: "ManipTrans: Efficient Dexterous Bimanual Manipulation Transfer via Residual Learning", Kailin Li, Puhao Li, Tengyu Liu, Yuyang Li, Siyuan Huang. arXiv v1, **27 Mar 2025**, cs.RO/cs.CV ([abs](https://arxiv.org/abs/2503.21860), [html v1](https://arxiv.org/html/2503.21860v1)). **CVPR 2025** ([CVF open access PDF](https://www.openaccess.thecvf.com/content/CVPR2025/papers/Li_ManipTrans_Efficient_Dexterous_Bimanual_Manipulation_Transfer_via_Residual_Learning_CVPR_2025_paper.pdf), [poster page](https://cvpr.thecvf.com/virtual/2025/poster/32548)). Project: [maniptrans.github.io](https://maniptrans.github.io/).

## 1. Core idea

Two-stage transfer of human MoCap hand–object trajectories to dexterous robot hands in IsaacGym. **Stage 1** trains a *general, object-free* hand trajectory imitator `I` on hand-only motion datasets (plus mirrored/interpolated synthetic data) with PPO — it learns to make the robot hand track MANO wrist pose + 21 keypoints. **Stage 2** freezes `I` and trains a task-specific **residual module** `R` whose state adds object/interaction information; the executed action is `a^t = a_I^t + Δa_R^t` (element-wise, then clipped to joint limits). `R` is zero-mean initialized with a warm-up so it starts near-identity. Training relaxes physics (zero gravity, high friction) and error thresholds, then anneals both. Reward design is deliberately task-agnostic. Output: **DexManipNet**, 3.3K robot episodes / 61 tasks / 1.2K objects / 1.34M frames, ~600 bimanual sequences. (§3, §3.4)

## 2. Observation representation

Three named groups per hand. Note they are **all fed to both actor and critic** — see caveat at the end of this section.

**Imitator state** `s_I^t = {τ_h^t, s_prop^t}`, `s_prop^t = {q_d^t, q̇_d^t, w_d^t, ẇ_d^t}` (§3.2). The reference `τ_h` = wrist 6-DoF pose `w_h ∈ SE(3)`, linear/angular velocities `ẇ_h = {v_h, u_h}`, MANO finger joint positions `j_h ∈ R^{F×3}` and velocities `j̇_h`. *"we normalize all translations relative to the dexterous hand's wrist position while preserving the original rotations to maintain the correct gravity direction."*

**Residual interaction state** (§3.3, verbatim):
```
s_interact^t = { τ_o^t, p_ô^t, ṗ_ô^t, m_ô^t, G_ô^t, BPS(ô), D(j_d^t, p_ô^t), C^t }
```
where `D(j_d^t, p_ô^t) = ||j_d^t − p_ô^t||²₂`, `m_ô` = center of mass, `G_ô` = gravitational force vector, `C` = fingertip contact force from sim, BPS = basis point set shape encoding. `s_R^t = s_I^t ∪ s_interact^t`.

Exact dims from [`main/cfg/task/ResDexHand.yaml`](https://github.com/ManipTrans/ManipTrans/blob/main/main/cfg/task/ResDexHand.yaml) and [`maniptrans_envs/lib/envs/tasks/dexhandmanip_bih.py`](https://github.com/ManipTrans/ManipTrans/blob/main/maniptrans_envs/lib/envs/tasks/dexhandmanip_bih.py):

```yaml
propObsDim: 13 + ndof*3          # obsKeys: q, cos_q, sin_q, base_state
privilegedObsDim: ndof + 13 + 5*4 + 3 + 1
privilegedObsKeys: [dq, manip_obj_pos, manip_obj_quat, manip_obj_vel,
                    manip_obj_ang_vel, tip_force, manip_obj_com, manip_obj_weight]
```
- `base_state` is 13 (pos 3 + quat 4 + lin vel 3 + ang vel 3) but **position is zeroed**: `torch.cat([torch.zeros_like(base_state[:, :3]), base_state[:, 3:]])` — "ignore base position".
- `manip_obj_pos` and `manip_obj_com` are expressed **relative to the wrist**.
- `tip_force` = 5 contact bodies × 4 = **20** (3-vector + its norm appended).
- `manip_obj_weight` = mass × |gravity.z| (1 dim).

**Target/reference block**, `TARGET_OBS_DIM` (per two hands, from `dexhandmanip_bih.py`):
```python
TARGET_OBS_DIM = (128 + 5 + (3+3+3+4+4+3+3 + (n_bodies-1)*9 + 3+3+3+4+4+3+3 + n_bodies)
                  * obs_future_length) * 2
```
concatenated in this exact order: `delta_wrist_pos, wrist_vel, delta_wrist_vel, wrist_quat, delta_wrist_quat, wrist_ang_vel, delta_wrist_ang_vel, delta_joints_pos, joints_vel, delta_joints_vel, delta_manip_obj_pos, manip_obj_vel, delta_manip_obj_vel, manip_obj_quat, delta_manip_obj_quat, manip_obj_ang_vel, delta_manip_obj_ang_vel, obj_to_joints, gt_tips_distance, bps`. BPS = 128 points (`bps_torch`, `bps_type="grid_sphere", n_bps_points=128, radius=0.2`), `gt_tips_distance` = 5.

**Future window**: `obsFutureLength: 1` in both task YAMLs — the reference window is the *next* frame only (`cur_idx + t for t in range(obs_future_length)`), though the field is configurable and the success check reserves "+3 for max future 3 steps".

**Worked example, Inspire (n_dofs=12, n_bodies=18), bimanual**: proprioception 49/hand → 98; privileged 49/hand (12+13+20+3+1) → 98; target 350/hand (128+5+23+153+23+18) → 700. Residual net additionally consumes the frozen imitator's sampled action, `(6 + n_dofs) × 2 = 36`.

⚠️ **Not a standard asymmetric actor-critic.** [`lib/rl/network_builder_residual_bih.py`](https://github.com/ManipTrans/ManipTrans/blob/main/lib/rl/network_builder_residual_bih.py) builds one shared `actor_mlp` feeding both `self.mu` and `self.value`, and explicitly `raise NotImplementedError("central_value not implemented")`. So "privileged" here is a grouping label, not a critic-only channel. Encoder: `SimpleFeatureFusion` over the three groups, `hidden_depth 3, hidden_dim 512, output_dim 256, swish`, then MLP `[256, 512, 128, 64]` ELU; `normalize_input: True`.
⚠️ Minor unverified oddity: `DexHandImitatorPPO.yaml` lists `privileged: 13+ndof*3` and `proprioception: ndof`, which is **swapped** relative to `DexHandImitator.yaml`'s `propObsDim`/`privilegedObsDim`. Cosmetic if the fusion just concatenates, but I could not confirm.

## 3. Action space

§3.1, verbatim: *"The action for each dexterous hand at time t, denoted as a^t ∈ A, comprises the target positions of each dexterous hand's joint a_q^t ∈ R^K for proportional-derivative (PD) control, and the 6-DoF force a_w^t ∈ R^6 applied to the robotic wrist"*, K = hand DoF.

Code: `numActions = (6 + n_dofs)` per hand, or `(1 + 6 + n_dofs)` with `useQuatRot` (false by default), `+3` if `usePIDControl`. Bimanual doubles it. Full action vector = `[base_action ‖ residual_action]`, split at the midpoint; `residual_action = actions[:, split:] * 2` → residual range **[-2, 2]** while base is [-1, 1].

Finger joints: `dof_pos = base + residual`, `clamp(-1,1)`, then `torch_jit_utils.scale(...)` to `[lower_limit, upper_limit]`, then EMA `actionsMovingAverage` (README uses **0.4**), then clamp again → `set_dof_position_target_tensor` (PD).

Wrist (floating base, force-controlled): via `apply_rigid_body_force_tensors`, with
```python
rh_force  = base[:, 0:3]*self.dt*self.translation_scale*500 + residual[:, 0:3]*self.dt*self.translation_scale*500
rh_torque = base[:, 3:6]*self.dt*self.orientation_scale*200 + residual[:, 3:6]*self.dt*self.orientation_scale*200
```
with `translationScale: 1.0`, `orientationScale: 0.1`, also EMA-smoothed. Optional `usePIDControl=True` mode replaces the 6 root dims with PID position/rotation error terms (9 dims; per-hand gains e.g. Inspire `Kp_pos=20, Ki_pos=0.005, Kd_pos=0.1; Kp_rot=0.5, Ki_rot=0.001, Kd_rot=0.01`), described in the code as *"reference only, not our main method."* Actions clipped at `clipActions: 1.0`; observations at `clipObservations: 5.0`.

**Control dt**: §4.2, *"simulating 4096 environments at a time step of 1/60 s"*. YAML: `sim.dt: 0.0166667`, `substeps: 2`, PhysX `num_position_iterations: 8`, `num_velocity_iterations: 1`, `contact_offset 0.005`, `rest_offset 0.0`, `max_gpu_contact_pairs 1048576`, `contact_collection: 1` (last substep only). **`controlFrequencyInv` defaults to 1** → no decimation, 60 Hz control. Data downsampled to 60 fps; the README notes the codebase is designed for 60 FPS data.

## 4. Rewards

**Stage 1 (imitator)**: `r_I^t = w_wrist·r_wrist^t + w_finger·r_finger^t + w_smooth·r_smooth^t`, with (Eq. 1, verbatim):
```
r_finger^t = Σ_{f=1..F} w_f · exp(−λ_f ||j_{d_f}^t − j_{h_f}^t||²₂)
```
`r_wrist` minimizes `w_d^t ⊖ w_h^t` and `ẇ_d^t − ẇ_h^t` (⊖ = SE(3) difference). `r_smooth` penalizes per-joint power (velocity ⊙ torque). Table 5 gives `(w_f, λ_f)` per finger as four values (proximal, intermediate, distal, tip): Thumb `0.5, 0.3, 0.3, 0.9` / `50, 40, 40, 100`; Index `0.5, 0.3, 0.3, 0.8` / `50, 40, 40, 90`; Middle `0.5, 0.3, 0.3, 0.75` / `50, 40, 40, 80`; Ring `0.5, 0.3, 0.3, 0.6` / `50, 40, 40, 60`; Pinky `0.5, 0.3, 0.3, 0.6` / `50, 40, 40, 60`. *"if a dexterous hand lacks a specific finger or joint (e.g., the Inspire Hand does not have distal joints), the corresponding parameters are set to zero."*

Code ([`dexhandimitator.py`](https://github.com/ManipTrans/ManipTrans/blob/main/maniptrans_envs/lib/envs/tasks/dexhandimitator.py), verbatim):
```python
reward_eef_pos        = torch.exp(-40  * diff_eef_pos_dist)
reward_thumb_tip_pos  = torch.exp(-100 * diff_thumb_tip_pos_dist)
reward_index_tip_pos  = torch.exp(-90  * diff_index_tip_pos_dist)
reward_middle_tip_pos = torch.exp(-80  * diff_middle_tip_pos_dist)
reward_pinky_tip_pos  = torch.exp(-60  * diff_pinky_tip_pos_dist)
reward_ring_tip_pos   = torch.exp(-60  * diff_ring_tip_pos_dist)
reward_level_1_pos    = torch.exp(-50  * diff_level_1_pos_dist)
reward_level_2_pos    = torch.exp(-40  * diff_level_2_pos_dist)
reward_eef_vel        = torch.exp(-1 * diff_eef_vel.abs().mean(dim=-1))
reward_eef_ang_vel    = torch.exp(-1 * diff_eef_ang_vel.abs().mean(dim=-1))
reward_joints_vel     = torch.exp(-1 * diff_joints_vel.abs().mean(dim=-1).mean(-1))
reward_eef_rot        = torch.exp(-1 * (diff_eef_rot_angle).abs())
reward_power          = torch.exp(-10 * target_states["power"])
reward_wrist_power    = torch.exp(-2  * target_states["wrist_power"])

reward_execute = (0.1*reward_eef_pos + 0.6*reward_eef_rot + 0.9*reward_thumb_tip_pos
  + 0.8*reward_index_tip_pos + 0.75*reward_middle_tip_pos + 0.6*reward_pinky_tip_pos
  + 0.6*reward_ring_tip_pos + 0.5*reward_level_1_pos + 0.3*reward_level_2_pos
  + 0.1*reward_eef_vel + 0.05*reward_eef_ang_vel + 0.1*reward_joints_vel
  + 0.5*reward_power + 0.5*reward_wrist_power)
```

**Stage 2 (residual)**: `r_R^t = r_I^t + w_object·r_object^t + w_contact·r_contact^t` (§3.3). `r_object` minimizes `p_ô^t ⊖ p_o^t` and `ṗ_ô^t − ṗ_o^t`. Contact reward (Eq. 2, verbatim):
```
r_contact^t = w_c · exp( −λ_c / Σ_{f=1..F} C_{d_f}^t · 1( D(j_{h_f}^t, p_o^t·o) < ξ_c ) )
```
with `w_c = λ_c = 1` (§D.2). Code adds the object terms:
```python
reward_obj_pos     = torch.exp(-80 * diff_obj_pos_dist)
reward_obj_rot     = torch.exp(-3  * (diff_obj_rot_angle).abs())
reward_obj_vel     = torch.exp(-1 * diff_obj_vel.abs().mean(dim=-1))
reward_obj_ang_vel = torch.exp(-1 * diff_obj_ang_vel.abs().mean(dim=-1))
contact_range = [0.02, 0.03]
finger_tip_weight = torch.clamp((0.03 - finger_tip_distance)/(0.03-0.02), 0, 1)
finger_tip_force_masked = finger_tip_force * finger_tip_weight[:, :, None]
reward_finger_tip_force = torch.exp(-1 * (1/(torch.norm(finger_tip_force_masked, dim=-1).sum(-1) + 1e-5)))
```
added to `reward_execute` with weights `+5.0*reward_obj_pos + 1.0*reward_obj_rot + 0.1*reward_obj_vel + 0.1*reward_obj_ang_vel + 1.0*reward_finger_tip_force`.

**Articulated-object extension** (§A.1): `τ_{o^A} = {p, ṗ, θ, θ̇}`; `r_{object^A}` adds `|θ_{o^A} − θ_{ô^A}|` and `|θ̇_{o^A} − θ̇_{ô^A}|`. *"Apart from this modification, the rest of the pipeline remains unchanged."*

**Curriculum / relaxation** (§3.3, §4.2): start with gravitational constant `G = 0` and friction `F` high, then restore. §4.2 verbatim: *"The initial threshold ε_finger is set to 6 cm and decays to 4 cm. Object alignment thresholds ε_object start at 90° and 6 cm for rotation and translation, gradually decreasing to 30° and 2 cm."* Implemented as `tightenMethod: exp_decay`, `tightenFactor: 0.7`, `tightenSteps: 3200` (residual) / `128000` (imitator):
```python
scale_factor = (np.e*2)**(-1*last_step/self.tighten_steps) * (1 - self.tighten_factor) + self.tighten_factor
```
Domain randomization in `ResDexHand.yaml`: gravity `const_scale init_value: 0` with `linear_decay, schedule_steps: 1920`; per-object friction `const_scale init_value: 3, upper_bound: 6.0, lower_bound: 1.0`, `linear_decay, schedule_steps: 1920`, `num_buckets: 250`, `frequency: 32`.

**Terminations** (RSI + early termination, §3.2/§3.3), exact code:
```python
failed_execute = ((
    (diff_obj_pos_dist > 0.02/0.343 * scale_factor**3)
  | (diff_thumb_tip_pos_dist  > 0.04 /0.7 * scale_factor)
  | (diff_index_tip_pos_dist  > 0.045/0.7 * scale_factor)
  | (diff_middle_tip_pos_dist > 0.05 /0.7 * scale_factor)
  | (diff_pinky_tip_pos_dist  > 0.06 /0.7 * scale_factor)
  | (diff_ring_tip_pos_dist   > 0.06 /0.7 * scale_factor)
  | (diff_level_1_pos_dist    > 0.07 /0.7 * scale_factor)
  | (diff_level_2_pos_dist    > 0.08 /0.7 * scale_factor)
  | (diff_obj_rot_angle.abs()/np.pi*180 > 30/0.343 * scale_factor**3)
  | torch.any((finger_tip_distance < 0.005) & ~(target_states["tip_contact_state"].any(1)), dim=-1)
 ) & (running_progress_buf >= 8)) | error_buf
```
The last clause is the **contact termination**: §3.3, *"if MoCap data indicates a firm grasp by the human hands (i.e., D(j_{h_f}^t, p_o^t·o) < ξ_t …), the contact force C_{d_f}^t must be non-zero. Failure to meet this condition results in early termination."* Here `ξ_t = 0.005` m. `error_buf` is a sanity check on velocity blowups (`|eef_vel|>100`, `|eef_ang_vel|>200`, `|joints_vel|>100`, `|dof_vel|>200`, plus object equivalents). Allegro relaxes `ε_finger` to **8 cm** (§A.2).

## 5. RL algorithm + simulator

**PPO** (Schulman et al.), actor-critic, in a **rl_games**-derived stack ([`lib/rl/`](https://github.com/ManipTrans/ManipTrans/tree/main/lib/rl)), on **IsaacGym Preview 4** (PhysX). §4.2 verbatim: *"We train both the imitation module I and residual module R using the Actor-Critic PPO algorithm, with a training horizon of 32 frames, a mini-batch size of 1024, and a discount factor γ = 0.99. Optimization employs Adam with an initial learning rate of 5×10⁻⁴ and a decay scheduler. All experiments are run in Isaac Gym, simulating 4096 environments at a time step of 1/60 s."*

[`ResDexHandPPO.yaml`](https://github.com/ManipTrans/ManipTrans/blob/main/main/cfg/rl_train/ResDexHandPPO.yaml): `gamma 0.99`, `tau 0.95`, `lr 5e-4` with `lr_schedule: warmup, warmup_steps: 10` (the imitator uses `adaptive`), `kl_threshold 0.008`, `e_clip 0.2`, `horizon_length 32`, `minibatch_size 1024`, `mini_epochs 5`, `critic_coef 4`, `grad_norm 1.0`, `entropy_coef 0.0`, `bounds_loss_coef 1e-4`, `use_soft_clamp: True`, `mix_ratio: 0.5`, `max_epochs 10000`, `early_stop_epochs` 500 default (README: 100 for simple tasks, 1000 for bimanual, "largely increase" for pen capping). Episode length: 1200 steps (residual) / 2000 (imitator). README overrides `learning_rate=2e-4`.

Object physics (§D.3): mass measured where possible, otherwise **density 200 kg/m³** ("approximating the average density of low-fill-rate 3D-printed models") with recomputed inertia; friction set *"slightly higher than the real-world value"* to compensate for missing skin compliance. Meshes made watertight with **ManifoldPlus**, collision via **CoACD** (`--max-convex-hull 32 -mi 2000 -md 5 -t 0.07`) for OakInk-V2; convex hull for the MoCap object meshes in §3.3.

## 6. Training cost

- **4096 parallel envs**, **1× NVIDIA RTX 4090** + Intel i9-13900KF, described as *"a personal computer"* (§4.2).
- Imitator pretraining: §C verbatim — *"We pre-train the hand imitation model on a large-scale training dataset … which takes approximately 1.5 days on a single GPU to obtain the reusable imitator."* This cost is amortized across all tasks.
- Residual fine-tuning: §4.3 verbatim — *"for an unseen single-hand manipulation trajectory of 60 frames ('rotating a mouse'), our method requires ∼15 minutes of training to achieve robust results, compared to QuasiSim's ∼40 hours of optimization."* §C adds that RL-Only *"still produces acceptable motions within 20 minutes"*, and Retarget+Residual is *"comparable … but requires slightly more time to converge"*.
- ⚠️ **Total environment steps are never reported.** Neither is per-task residual training time for bimanual tasks (only the 60-frame single-hand example).

## 9. Limitations + issue tracker

**Paper §5 "Discussion and Limitations", verbatim**: *"Although ManipTrans successfully handles most MoCap data, some sequences cannot be transferred effectively. We attribute this to two main reasons: 1) excessive noise in interaction poses and 2) insufficiently accurate object models for simulation, particularly for articulated objects."*

Other limitations stated in-text: no quantitative comparison with QuasiSim is possible (*"their full pipeline has not yet been released, and their 'randomly' selected validation set is not available"*); RL-combined baselines had to be reimplemented (*"Due to the lack of publicly available code for prior RL-combined methods"*); evaluation excludes deformable/oversized objects and is limited to 4–20 s clips (~80 episodes); §D.3 concedes *"Accurately simulating contact-rich scenarios remains an area for future exploration."* Robustness degrades with input noise (§B, Table 4): bimanual SR drops 39.5 → 30.1 → 19.5 at σ = 0.5 / 1.0 cm, though it rebounds to 39.2 at σ = 1.5 cm — an odd non-monotonicity the paper does not comment on.

**GitHub issues** (12 total: 2 open, 10 closed):
- **#78** (open) "About shadow hand retargeting"; **#74** (open) "Out of memory when evaluating".
- **#69** "Poor performance on full GRAB Dataset" — the most substantive: a user reports success only on "airplane fly", with *"The resulting wrist positions do not follow the ground truth"*, *"The fingers are not really moving or cannot generate the necessary force for grasping"*, unwanted wrist rotations, and a counterintuitive scaling result (training on 3 tasks > 85 tasks > 1300+ tasks). No author response visible.

## 10. Metrics

§4.1, verbatim (*"adapted from [QuasiSim] but … more stringent due to the complexity of our bimanual tasks"*):

**1) Per-frame Average Object Rotation and Translation Error**
```
E_r = (1/T) Σ_{t=1..T} ( p_rot_ô^t · (p_rot_o^t)^{-1} )
E_t = (1/T) Σ_{t=1..T} || p_tsl_ô^t − p_tsl_o^t ||²₂
```
*"Errors E_r and E_t are reported in degrees and centimeters."*

**2) Mean Per-Joint Position Error (in cm)**
```
E_j = (1/(T·F)) Σ_{t=1..T} Σ_{f=1..F} || j_{d_f}^t − j_{h_f}^t ||²₂
```

**3) Mean Per-Fingertip Position Error (in cm)**
```
E_ft = (1/(T·M)) Σ_{t=1..T} Σ_{ft=1..M} || t_{d_ft}^t − t_{h_ft}^t ||²₂
```
*"Here, M equals 5 for single-hand tasks and 10 for bimanual tasks."* F = 21 keypoints per hand (fingertips, palm, phalanges), manually selected (§4.2, §D.1: human fingertips are the midpoint of the three tip anchors; robot fingertips are the points of maximum curvature along the central axis of the finger pads).

**4) Success Rate (SR)**, verbatim: *"A tracking attempt is deemed successful if E_r, E_t, E_j, and E_ft are all below the specified thresholds: **30°, 3 cm, 8 cm, and 6 cm**, respectively. For bimanual tasks, the trajectory is considered failed if either hand fails to meet these conditions, making the success criterion stricter compared to single-hand tasks."*

Note the `||·||²₂` notation in E_t/E_j/E_ft literally reads as squared L2 yet the units are cm — I'd read this as a typography artifact for L2 distance; the paper does not clarify.

# Cross-cutting notes

- **DexMachina explicitly reimplements ManipTrans as a baseline** (§B.3) and reports it *"achieves no clear improvements over the no-curriculum setting, and training is less stable: … the ManipTrans policy initially achieves high task reward, but performance drops as the curriculum progresses and cannot recover."* Caveat: this is a reimplementation of only the *curriculum* (threshold + gravity + friction decay) grafted onto DexMachina's hybrid actions/rewards in Genesis, on **articulated** ARCTIC objects — ManipTrans's own ARCTIC results are qualitative only (§A.1) and its articulated-object code is unreleased (issue #71). ManipTrans is called "concurrent work" (both are March/May 2025).
- The two use different metrics and are **not directly comparable**: DexMachina = ADD-AUC over object mesh vertices, 1–9 cm threshold sweep, articulated objects only, no hand-pose term; ManipTrans = thresholded 4-way SR (30°/3 cm/8 cm/6 cm) with explicit hand-fidelity terms, rigid objects, MPJPE-style E_j/E_ft.
- Simulators differ (Genesis vs IsaacGym), which DexMachina cites as the reason it could run 12,000 envs vs *"2048 for ObjDex and 4096 environments for ManipTrans"*.
- **Licensing asymmetry matters**: DexMachina is MIT; ManipTrans code, checkpoints, and DexManipNet are all **GPL-3.0**.
