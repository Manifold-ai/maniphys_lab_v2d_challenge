# RL Object-Trajectory Tracking with Dexterous Hands — Technical Survey

**Framing for your challenge (G1 + Dex3, Isaac Lab, scored on ADD-AUC / SR / per-frame object pose error):** the literature splits cleanly into three embodiment regimes that have *very* different object-tracking accuracy profiles. Ranked by direct transferability to your setup:

| Tier | Systems | Why |
|---|---|---|
| **Directly reusable** | **Weave** (Isaac Lab, G1 29-DoF + 12 finger DoF, object-pose reward, code live & pushed today), **CoorDex** (Isaac Lab, G1 + Dex3-1 hand prior), **GRAIL** (Isaac Lab, G1, 7 finger DoF/hand ≈ Dex3), **InterMimic** (has `omomo_g1_29dof_with_hand` task + Isaac Lab port) | Same sim, same robot class, object-pose in reward |
| **Reward/curriculum donors** | **DexMachina** (defines ADD-AUC; ships a **Dex3 asset**), **ManipTrans**, **DexTrack**, **Dexplore**, **ResMimic**, **CHORD**, **REGRIND** | Floating-wrist/fixed-base, but the reward math ports 1:1 |
| **Background** | PhysHOI, DeVI, InterPrior, ObjDex, DexterityGen, TopoRetarget, DexMan, HumDex | Simulated character, non-G1 hardware, or not object-tracking |

**The single most important empirical fact in this literature (see §B):** whole-body balance and object tracking are *directly antagonistic* under a shared reward, and every recent paper that measured it found the same thing — the variant with the **best body tracking has the worst object tracking**.

## 1. Per-system dossiers

### PhysHOI — Physics-Based Imitation of Dynamic HOI (basketball)
- **What:** first task-reward-free physics-based whole-body HOI imitation; introduces the *contact graph* + *interaction graph* rewards; BallPlay dataset (8 basketball skills).
- arXiv: https://arxiv.org/abs/2312.04393 · GitHub: https://github.com/wyhuai/PhysHOI · Project: https://wyhuai.github.io/physhoi-page/
- **License:** NVIDIA License (`LICENSE.txt`, GitHub reports NOASSERTION) — derived from Isaac Gym / ASE.
- **Sim:** Isaac Gym Preview 4. **Embodiment:** FULL HUMANOID — SMPL-X kinematic tree, 51×3 DoF actuators, fully dexterous hands. **Hands:** SMPL-X MANO fingers (not a robot hand).
- **Weights:** yes, Google Drive (per-task `PhysHOI.pth` for toss/fingerspin/pass/walkpick/backspin/rebound/changeleg/backdribble).
- **Maintenance:** dormant — last commit 2024-09-04, 247 stars.
- **Object-centric reward** (`physhoi/env/tasks/physhoi.py::compute_humanoid_reward`) — **fully multiplicative**:
  ```
  rb  = rp*rr*rpv*rrv          # body pos/rot/vel
  ro  = rop*ror*ropv*rorv      # object pos/rot/vel
  rig = exp(-eig*w['ig'])      # interaction graph: (keypoint - obj_pos) vectors
  rcg = rcg1*rcg2              # contact graph: body-no-contact, object-contact
  reward = rb*ro*rig*rcg
  ```
  with `eop = mean((ref_obj_pos - obj_pos)**2)`, `rop = exp(-eop*w['op'])`.
  Weights (`physhoi/data/cfg/physhoi.yaml`): `p:50, r:50, pv:0, rv:0, op:1, or:0, opv:0, orv:0, ig:20, cg1:5, cg2:5`.
  Note `or:0` — object **rotation is not rewarded at all** in the released basketball config; the `ig` term (weight 20) carries the relative hand-object geometry. Contact is approximated by force thresholds (`>0.1 N`) because Isaac Gym had no GPU collision-detection API.

### ManipTrans (CVPR 2025) + DexManipNet
- **What:** two-stage — generalist hand-trajectory imitator pretrained on hand-only data, then a **residual module** fine-tuned under interaction constraints. Produced DexManipNet (3.3K robot episodes, incl. pen capping, bottle unscrewing).
- arXiv: https://arxiv.org/abs/2503.21860 · GitHub: https://github.com/ManipTrans/ManipTrans · Weights: https://huggingface.co/LiKailin/ManipTrans
- **License: GPL-3.0** (viral — matters if you plan to build on it).
- **Sim:** Isaac Gym, 4096 envs, dt=1/60. **Embodiment:** FLOATING WRIST — action is `a_q` (PD joint targets) **plus a 6-DoF wrist force** `a_w`; README exposes "6D-Force mode" vs "PID-controlled mode".
- **Hands:** Inspire, Inspire FTP, Shadow, Allegro, XHand, ArtiMano. (XHand/Inspire-FTP URDFs withheld for licensing.)
- **Weights:** imitator checkpoints released on HF; residual policies not.
- **Maintenance:** last commit 2025-06-18, 339 stars, 4 open issues.
- **Reward design:**
  - Imitation stage: `r_I = w_wrist·r_wrist + w_finger·r_finger + w_smooth·r_smooth`, with
    `r_finger = Σ_f w_f · exp(-λ_f ‖j_{d,f} - j_{h,f}‖²₂)` over F=21 keypoints, weights biased toward thumb/index/middle fingertips. Smoothness penalizes joint power (velocity ⊙ torque).
  - Residual stage: `r_R = r_I + w_object·r_object + w_contact·r_contact`.
    `r_object` minimizes `p_ô ⊖ p_o` and `ṗ_ô − ṗ_o` (SE(3) pose + velocity).
    **Contact-force reward** (Eq. 2): `r_contact = w_c · exp( −λ_c / Σ_f C_{d_f} · 1[D(j_{h_f}, p_o·o) < ξ_c] )` — i.e. reward grows as fingertip contact *force* grows, but only on fingers the MoCap says should be touching.
  - **Curriculum (the "quasi-physical relaxation"):** gravity **G set to 0 → restored to 9.81**, friction **F set high → reduced**, and ET thresholds annealed `ε_finger 6→4 cm`, `ε_object 90°→30°` and `6→2 cm`. Ablation: *"Without initial relaxation of the threshold constraints, the network may fail to converge entirely."*
  - Metrics: per-frame `E_r` (deg), `E_t` (cm), `E_j`, `E_ft`; SR requires all four under 30°/3 cm/8 cm/6 cm.
  - DexMachina's reimplementation (`dexmachina/envs/maniptrans_curr.py`) pins the numbers: `gravity_range [9.81, 0.005]`, `friction_range [5.0, 1.0]`, `eps_finger [0.06, 0.04]`, `eps_object_P [0.06, 0.02]`, `eps_object_R [1.57, 0.52]`.

### DexMachina (2505.24853, ICML 2026)
- **What:** "functional retargeting" — track *object* states from human bimanual demos of articulated objects. **Defines the ADD-AUC metric your challenge uses.** Ships a 6-hand × 5-object ARCTIC benchmark.
- arXiv: https://arxiv.org/abs/2505.24853 · GitHub: https://github.com/MandiZhao/dexmachina · Docs: https://mandizhao.github.io/dexmachina-docs · Project: https://project-dexmachina.github.io
- **License: MIT.** 264 stars, last commit 2026-03-23. RL eval code still on TODO list.
- **Sim: Genesis** (custom fork `MandiZhao/Genesis`) + rl_games PPO, 12,000 envs, L40s/H100.
- **Embodiment: FLOATING WRIST.** Each hand gets 6 virtual wrist joints — see `dexmachina/envs/hand_cfgs/dex3.py`: `dex3_left_6dof.urdf`, actuators `wrist_rot` (`[LR]_forearm_(roll|pitch|yaw)_link_joint`, kp=200) and `wrist_trans` (`[LR]_forearm_t[xyz]_link_joint`, kp=300).
- **Hands: Ability, Allegro, DexRobot, Inspire, Schunk SVH, XHand, and — critically for you — Unitree `dex3_hand`** (assets at `dexmachina/assets/dex3_hand/dex3_left_6dof.urdf`, confirmed HTTP 200). `kpt_link_names` for Dex3 = palm + thumb_0/1/2 + middle_0/1 + index_0/1.
- **Weights:** none released (hand + ARCTIC assets and training script only).
- **Object-centric reward — this is the canonical formulation for your challenge:**
  ```
  d_pos = ‖ĝᵀ − gᵀ‖₂ ;  d_rot = 2·acos(|⟨ĝᴿ, gᴿ⟩|) ;  d_ang = ‖ĝᴶ − gᴶ‖₂
  r_task = r_pos · r_rot · r_angle
         = exp(−β_pos d_pos)·exp(−β_rot d_rot)·exp(−β_ang d_ang)     # PRODUCT, not sum
  r_imi  = (1/K) Σ exp(−β_imi ‖x̂_i − x_i‖₂)                          # retargeted keypoints
  r_bc   = (1/J) Σ exp(−β_bc ‖q̂_i − q_i‖₂)                           # behavior cloning to retargeted joints
  r_con  = (1/2NK) Σ_side Σ_{i,j} exp(−β_con D^{(i,j)})               # contact position matching
  r_t = λ_task·r_task + λ_imi·r_imi + λ_bc·r_bc + λ_con·r_con
  ```
  `D` is masked: set to `d_max` when demo/policy contact masks disagree, 0 when both say "no contact".
  **Actual values from `examples/train_rl.sh`:** `--task_rew_betas 10 1 5` (β_pos=10, β_rot=1, β_arti=5), `-imi 0.3 -bc 0.3 -con 3`, `--contact_beta 10`. Code defaults in `rewards.py`: `obj_pos_beta 20, obj_rot_beta 5, obj_arti_beta 20, imi_fingertip_beta 20, bc_beta 500, contact_beta 30`.
  **Hybrid action:** wrist = retargeted value + policy residual (`hybrid_scales 0.1`), fingers = absolute normalized targets (scale 1.0). Reported as a large learning-efficiency win.
- **Virtual Object Controller (VOC) — the key curriculum, copied by everyone since:** object gets 6 virtual 1-DoF base joints + 1 articulation joint, all PD-actuated toward the demo trajectory. `kp_init=1000, kv_init=10, force_range_init=50` in `curriculum.py` (the example script uses `--kp_init 80 --kv_init 5`). **Annealing is reward-gated, not time-gated:** gains decay by `φ_p` only when all four normalized rewards exceed thresholds `σ = {task 0.5, con 0.05, imi 0.05, bc 0.05}` (example script: `--curr_rew_thres 0.6 0.01 0.01 0.01`); `k_p ≤ 0.01 → k_p = k_v = 0`; hard stop at `zero_epoch=30000`. There is also a "dialback" mechanism that partially restores gains (×0.98) if episode length collapses.
- **Why ADD-AUC:** *"success rate reporting is based on how many timesteps… within given error thresholds, hence the results are highly sensitive to the threshold values (this case requires 3 different thresholds for position, rotation, and joint angle errors)… we propose to follow prior work in object pose tracking and use a similar ADD-AUC metric… we compute ADD for each object part separately and average ADD results before computing AUC."* They explicitly do **not** use ADD-S because exact target correspondences exist.

### DexTrack (ICLR 2025)
- **What:** generalizable neural tracking controller + data flywheel (RL ⊕ IL) + per-trajectory homotopy optimization.
- arXiv: https://arxiv.org/abs/2502.09614 · GitHub: https://github.com/Meowuu7/DexTrack · Project: https://meowuu7.github.io/DexTrack/
- **License:** BSD-3-Clause (inherited from NVIDIA IsaacGymEnvs). 132 stars, last commit 2026-04-14.
- **Sim:** Isaac Gym + rl_games PPO, 8192 envs. **Embodiment: FLOATING-BASE HAND** — *"we additionally add three translation joints and three revolute joints to control the global position and orientation of the hand"*, θ ∈ ℝ²² for Allegro/LEAP. Real robot = LEAP on a Franka.
- **Hands:** Allegro (sim), LEAP (real). **Datasets:** GRAB (1,269 retargeted seqs), TACO (2,316).
- **Weights:** yes — OneDrive checkpoints + per-sequence ckpts (`s2_cubesmall_inspect_ckpt.pth` etc.).
- **Reward** (Appendix A.2) — **linear, not exponential**, which is unusual:
  ```
  r = w_op·r_op + w_oq·r_oq + w_wrist·r_wrist + w_finger·r_finger + w_affinity·r_affinity
  r_op    = 0.9 − ‖p_n^o − p̂_n^o‖₂
  r_oq    = π − Diff_Angle(q_n^o − q̂_n^o)
  r_wrist = −( w_trans·‖s^h[:3] − ŝ^h[:3]‖₁ + w_ornt·‖s^h[3:6] − ŝ^h[3:6]‖₁ )
  r_finger= −w_finger·‖s^h[6:] − ŝ^h[6:]‖₁
  ```
  Weights: `w_op=1.0, w_oq=0.33, w_wrist·w_trans=0.3, w_wrist·w_ornt=0.05, w_finger=0.05`. Plus a **+1 bonus when rotation error <5° and translation error <5 cm**.
  **No velocity terms, deliberately:** *"it is impossible for us to get accurate velocities from kinematic references… we do not use them to avoid unnecessary noise."*
  Action space is a *cumulative* residual: `a_n = s_n^b + Σ_{k≤n} Δa_k`.
  IL loss added on top of PPO: `L_a = E‖a_n − a_n^L‖`.
- **Metrics:** `R_err` (rad), `T_err` (cm), `E_wrist`, `E_finger`, SR at two thresholds (10 cm-20°-0.8 and 10 cm-40°-1.2). GRAB: 0.4515 rad / 4.82 cm / 42.6–61.4% SR.

### Dexplore (2509.09671)
- **What:** collapses retarget→track→correct into one loop; treats demos as *soft guidance* via adaptive "reference scopes" instead of hard tracking rewards.
- arXiv: https://arxiv.org/abs/2509.09671 · **No public code** (checked `Meowuu7` org and HF — nothing).
- **Sim:** Isaac Gym, 4096 envs, sim 1/60 / control 1/30. **Embodiment: FLOATING WRIST** — *"the wrist is modeled as a floating root joint in world coordinates"*; 6-DoF residual wrist offset + local finger PD targets, with mimic-joint coupling for Inspire.
- **Hands:** Inspire RH56DFTP (12 joints / 6 actuated), Allegro (16 DoF). Real: Inspire + xArm-7. **Dataset:** GRAB (+ TACO zero-shot).
- **Reward:**
  ```
  R_J^h = exp(−Σ λ_J ‖M(p̂) − M(p)‖²)      # mapped hand joint positions
  R_R^h = exp(−Σ λ_R ‖M(R̂) ⊖ M(R)‖²)
  R_p^o, R_R^o                              # object position / orientation
  R_D   = exp(−λ_D ‖D̂ − D‖²)               # hand-joint → nearest object surface vectors
  R_C   = exp(−λ_C ‖Ĉ − C‖²)               # binary per-link contact indicators
  + R_energy(a_t)                           # ΔPD-target, joint accel, joint vel penalties
  ```
  **Reference-Scoped Exploration (RSE), the novel bit — two coupled schedules:**
  1. *Distance-modulated weights:* `w(D) = min(1, D / 0.20 m)` — kinematic matching weight is **proportional to hand-object distance**, energy penalty **inversely proportional**. Far from the object → track the reference; near the object → let the robot deviate and do what physically works.
  2. *Failure-rate-adaptive ET thresholds:* `κ = κ_init · N_fail / N_total`, tightened online.
  Termination: `R_J^h < κ_J`, `R_p^o < κ_p^o`, `R_R^o < κ_R^o`, `R_D < κ_D`, or contact mismatch for 10 consecutive frames.
- **Numbers (Inspire hand, GRAB):** Dexplore **87.7% SR** vs Dexplore-w/o-RSE 29.9% vs DexTrack+AnyTeleop 7.4% vs DexTrack+their-retarget 69.8%. Allegro: 78.7% vs 29.9% vs 45.9% vs 77.4%. **RSE alone is worth +48 to +58 pp SR** — the largest single-design-choice gain in this whole survey.

### InterMimic (CVPR 2025) — **the most directly reusable G1 codebase of the older generation**
- arXiv: https://arxiv.org/abs/2502.20390 · GitHub: https://github.com/Sirui-Xu/InterMimic · Project: https://sirui-xu.github.io/InterMimic/
- **License: MIT.** 530 stars, last commit 2026-04-21 — actively maintained.
- **Sim: Isaac Gym AND Isaac Lab.** README: *"[2025-12-17] Isaac Gym checkpoints are compatible with IsaacLab inference?! Check out the newly released implementation."* Recommended: Isaac Sim 5.1.0 + IsaacLab v2.3.1.
- **Embodiment: FULL HUMANOID.** Two variants shipped: SMPL-X (52 bodies) and **`g1_29dof_with_hand`** (`env/tasks/intermimic_g1.py`, `data/cfg/omomo_g1_29dof_with_hand.yaml`, `robotType: 'g1/g1_29dof_with_hand.urdf'`, `numDoF: 43`, `numDoFWrist: 3`, `numDoFHand: 7` → **7 finger DoF per hand = Dex3-class three-finger hand**). - **Weights:** yes — teacher policy checkpoints + high-fidelity-physics checkpoint released; PSI + processed OMOMO data released.
- **Reward (`env/tasks/intermimic.py`), fully multiplicative, four blocks:**
  - `compute_humanoid_reward` → `rb = rp·rr·rpv·rrv·energy`, with **distance-modulated weights**: `weight_h = exp(−5·‖ref_ig‖)`, position error weighted by `weight_hp` (=1 forced for ankle/toe), rotation error weighted by `weight_hr = 1 − weight_h`. *Near the object → track positions; far → track rotations.*
  - `compute_obj_reward` → `ro = rop·ror·ropv·rorv·obj_energy`. **Crucially, the object pose is expressed in the humanoid's own root/heading frame**: `local_obj_pos = quat_rotate(heading_rot, obj_pos − root_pos)` with world z preserved; same for `local_obj_rot`.
  - `compute_ig_reward` → interaction graph over all (keypoint × object-surface-point) pairs, with inverse-square-distance normalized weights `weight_1 + weight_2`, `rig = exp(−w_ig · 0.5·Σ eig)`.
  - `compute_cg_reward` → contact graph split into hand / other / all-body blocks, gated by reference contact; plus `contact_energy = exp(−w_eg3·‖F‖²)` to penalize slamming.
  - Terminations: object points deviate >0.5 m, weighted joint-to-surface distance >0.5 m from reference, or **required contact lost for >10 consecutive frames**.
- **⚠️ The single most actionable number for your challenge** — compare the released weight configs:
  | config | `p` | `r` | `op` | `or` | `opv` | `ig` |
  |---|---|---|---|---|---|---|
  | `omomo_train_new.yaml` (SMPL-X) | 30 | 1.5 | **5.0** | 0.1 | 0.1 | 5 |
  | `omomo_g1_29dof_with_hand.yaml` (**G1**) | 10 | 10 | **0.0** | 0.1 | 0.01 | **20** |
  Since `rop = exp(−eop·w['op'])`, `op: 0` means **absolute object-position tracking is switched off entirely on the real-robot embodiment**, and the object signal is carried by the interaction graph (weight 20, 4× the SMPL-X value) plus contact. That is the authors' own answer to "whole-body balance fights object tracking": stop rewarding world-frame object position on the robot and reward *relative* hand-object geometry instead.
- Also: PSI (Physical State Initialization) — FIFO buffer of high-reward simulated states, mixed with RSI; and IET (Interaction Early Termination).

### InterPrior (2602.06035)
- arXiv: https://arxiv.org/abs/2602.06035 · Project: https://sirui-xu.github.io/InterPrior/ · **No repo yet** (checked `Sirui-Xu/InterPrior` → 404).
- Isaac Gym. SMPL (51×3 action) **and Unitree G1 (29-dim action, 39 rigid bodies)**. Datasets: OMOMO / BEHAVE / InterAct.
- **InterMimic+ expert reward:** `r_t = (r_track · r_energy · r_h) + r_ter`, with `r_ter = −w_ter·c_ter`.
- **The hand-opposition reward `r_h`** (Sec. D.1) — the formulation Weave cites as "[10]":
  ```
  u_T = (p_T − q_T)/‖p_T − q_T‖          # thumb tip minus nearest object surface point
  u_j = (p_j − q_j)/‖p_j − q_j‖          # other fingertips
  e_h = 1 − (1/|S|) Σ_j (1 − u_Tᵀ u_j)/2
  r_h = exp(−w_h · e_h)
  ```
  `w_h` **increases as hand-object distance decreases**, and the term only activates when the reference indicates upcoming interaction. This is *reference-free* — it uses the live simulated object pose, so it still guides the fingers when the reference is wrong or the rollout has drifted. Explicitly introduced because *"the policy shows a degradation of precision when interacting with thin or small objects, as it tends to rigidly follow reference trajectories."*
- Also: latent hyperspherical projection `z ← z/‖z‖`, masked residual goal encoding, sparse-impulse perturbations to pelvis and object during rollouts.

### DeVI (2604.20841) — physics-based dexterous HOI from *synthetic video*
- arXiv: https://arxiv.org/abs/2604.20841 · Project: https://snuvclab.github.io/devi/
- Isaac Gym, simulated humanoid with dexterous hands (SMPL-X class). Dataset: GRAB for evaluation.
- **Hybrid tracking reward, fully multiplicative:**
  `R = R_h · R_o · R_contact`, `R_h = r_jp·r_jv·r_jr·r_lp^h·r_lr^h·r_pw` (local hand terms are wrist-centric), `R_contact = R_cf · R_cd` gated by a binary contact label ψ_t inferred from **2D object point motion in the generated video**.
- **The object term is 2D:** `R_o = exp(λ_o‖x̂_t − x_t‖²)` where `x_t` is the **image-space projection of the simulated object's visible vertices**. Novel — no 3D object GT needed.
- Numbers (GRAB): DeVI 25.35 mm MPJPE-all / 35.6 mm T_obj / 0.60 O_obj vs PhysHOI 142.6 / 94.3 / 1.396, SkillMimic 136.1 / 103.4 / 0.889, InterMimic 91.1 / 91.5 / 0.891. Ablation `DeVI w/o 2D reward`: 116.2 / 103.0 / 1.120 — the 2D object reward is load-bearing.

### DexMan (2510.08475)
- arXiv: https://arxiv.org/abs/2510.08475 · GitHub: https://github.com/EmbodiedAI-NTU/DexMan · Project: https://dexman2026.github.io/ (also `embodiedai-ntu.github.io/dexman`)
- **No LICENSE file** (all-rights-reserved by default). 48 stars, last commit 2026-03-13.
- **Sim:** Isaac Gym (RL) + Genesis (IK for wrist retargeting), rl_games PPO, 2048 envs, 30 Hz control, 500 iters.
- **Embodiment: FULL HUMANOID — Unitree G1 + two Shadow Hands**, but *"keeping the lower body fixed since tabletop tasks do not involve lower-body motion."* This is the pragmatic middle ground: real robot kinematics, no balance problem.
- **Reward:** `R = R_contact + R_obj + R_imit`.
  - **Contact-Prior Attraction (the novelty):**
    ```
    R_contact = (1/|O|) Σ_{(j,o)∈P(t)} w_c^j (1 + γ_c^j ⟨n_{j,t}^rob, d̂_{j,t}^o⟩)
                · exp(−λ_c ‖p_{j,t}^rob − v_{j,t}^o‖²₂) · (w_c1 + w_c2·1_lifted^o)
    ```
    where `v_{j,t}^o` is the **object mesh vertex** the human fingertip *j* was nearest to (extracted offline, thresholded by τ_j), and the `⟨n, d̂⟩` term is a directional-alignment factor that kills back-of-hand contacts. Explicitly contrasted with DexMachina: *"In contrast to rewards based on static, world-space coordinates (Mandi et al., 2025), its object-centric nature makes the learned policy inherently robust to variations in the object's pose."*
  - **Object-following:** `R_obj = (1/|O|) Σ (w_pos·e^{−λ_pos Δ_pos} + w_rot·e^{−λ_rot Δ_rot})·(w_o1 + w_o2·1_lifted)` — note the **lifted-object bonus multiplier** on both contact and object rewards.
  - **Imitation:** `R_imit = w_pos·e^{−λΔ_pos} + w_rot·e^{−λΔ_rot} + w_jnt·Σ e^{−λΔ_jnt}`.
  - Policy outputs residuals `{Δx^h, Δω^h, Δθ^h}` to wrist position/orientation/finger angles, converted through the same IK solvers.
- **Ablations (the strongest contact-reward evidence anywhere):** TACO SR 27.4% → **7.2% without contact reward** (and 18.4% without task reward); Veo3 synthetic 39.0% → **7.8% without contact reward** (34.6% without task). *"contact guidance is the dominant factor."* Note the perverse metric behavior: w/o contact reward, `E_r` and IoU **improve** (0.182 rad, 61.9%) because only the easy successes survive — a warning for how you read conditional-on-success metrics.
- Beats ManipTrans by **+19 pp SR** on OakInk-v2 (77 val sequences, 10 rollouts each, per-timestep success needs <0.5 rad and <3 cm) *despite controlling a full humanoid rather than floating hands*.

  | All Joint Space | **0** | 1.00 | 0.00 | 0.86 | 0.04 |

  | **CoorDex** | **0.55** | 1.00 | 0.55 | 0.00 | 0.00 |
  Joint-space finger control on a walking humanoid → 0–1% grasp rate. The body prior alone is *not enough*; you need a hand prior too. Also: the failing variants "learn to slow down or stop near the bottle and try to solve the problem as a stationary grasping task."

  ```yaml
  motion_anchor_pos:  {weight: 1.0, std: 0.3}   # pelvis position
  motion_anchor_ori:  {weight: 1.0, std: 0.4}   # pelvis orientation (geodesic)
  motion_body_pos:    {weight: 1.0, std: 0.3}

  object_ori:         {weight: 2.0, std: 0.3}   # ∠(R^o, R̂^o)²
  hand_opposition:    {weight: 2.0, thumb_body_name: thumb_distal,
                       finger_body_names: [index_intermediate, middle_intermediate,
                                           ring_intermediate, pinky_intermediate]}
  contact:            {weight: 2.0, saturate_force: 5.0,
                       hand_body_names: [".*_thumb_intermediate", ".*_thumb_distal",

                                         ".*_ring_intermediate", ".*_pinky_intermediate"]}

  feet_slide:         {weight: -1.0}
  ```

  Tracking terms are `w_i·exp(−e_{t,i}/σ_i²)`. Object weight is **2× body weight**.
  - **Hand opposition:** `Σ_h η_{t,h}·[ (1/|K_h|) Σ_k (1 − u_{t,h,0}ᵀ u_{t,h,k})/2 ] / (Σ η + ε)` with `u` = surface-to-fingertip unit vectors, `k=0` = thumb, `η` = expected-contact gate.

This is a gradient-scale fix for exactly the body-vs-object conflict.
- Results: 9 objects, 7,869 train trajs (19.56 h) / 1,605 test (3.67 h). Train split 78.0% SR @10k iters → **92.5% @100k**, object rotation 11.17° → **7.18°**, object position 5.17 cm → **4.27 cm**. Unseen: **65.0% SR / 84.5% progress**. Joint multi-object policy 95.3% pooled vs 91.5% for 9 specialists at matched total iterations. *"Lower imitation error does not imply more reliable interaction completion, which argues against using tracking error alone as the primary metric."*
- Pipeline: GMR-style whole-body IK (pelvis constrained only in horizontal plane, height from ground contact) → contact-aware hand refinement minimizing `λ_a·contact-attraction − λ_q·Q̂_FC(force-closure) + λ_p·penetration + L_reg` → Kimodo approach-motion prefix (K=3 train / K=5 test azimuths).

## (A) Object-centric reward design — what's actually standard

**The canonical term set, in descending order of universality:**

1. **Object position / orientation exponential tracking.** Universal. Two camps:
   - *Product of exponentials* (ObjDex → DexMachina → PhysHOI/InterMimic/DeVI): `exp(−β_p d_pos)·exp(−β_r d_rot)·exp(−β_a d_ang)`. DexMachina's stated reason: *"encouraging balanced learning"* — a product cannot be gamed by maxing one component. Note `rewards.py` has both modes: `task_rew = w·r_pos·r_rot·r_arti` (multiply) or `w·(w_p r_pos + w_r r_rot + w_a r_arti)` (sum); default is multiply.
   - *Weighted sum of exponentials* (Weave, GRAIL, TopoRetarget, DexMan, ResMimic, HDMI). Easier to tune per-term σ; Weave sets object weights 2× body weights, TopoRetarget sets object 8× everything.
   - *Linear* (DexTrack: `r_op = 0.9 − ‖Δp‖`, `r_oq = π − Δangle`) — rare; plus a sparse +1 bonus at 5 cm/5°.
   - **Geometric alternatives that replace pose difference entirely:**
     - ResMimic: **point-cloud** reward `exp(−λ_o Σ_i ‖P[i]_t − P̂[i]_t‖₂)` over N mesh-surface points. *"an alternative with smoother reward landscape… naturally accounts for both translation and rotation, eliminating the need for task-specific weight tuning."*
     - REGRIND: object **keypoint** mean L2, `exp(−ε/σ)`, σ=0.02, w=1.5. Works for rigid + articulated uniformly.
     - TopoRetarget: 6 object axis-points.
     - InterMimic/PhysHOI: object-point cloud used in the ET check and in the interaction-graph reward.
     - DeVI: **2D image-space projection** of visible object vertices.
   - **Frame matters.** InterMimic computes object pose in the humanoid's heading frame; HDMI, TopoRetarget, Weave, GRAIL all use robot/base-frame object observations. GRAIL measured the cost of *not* doing this: **−23.5 pp SR** (57.9% vs 81.4%).

2. **Contact matching.** Second-most universal, and empirically the highest-leverage single term.
   - *Position-matched* (DexMachina): mask-gated L2 between policy contact positions and demo contact positions, `exp(−β_con D)`; `D = d_max` on mask disagreement.
   - *Force-magnitude-matched* (Weave): `1 − |y − min(‖f‖/f̄, 1)` with ternary reference labels {−1, 0, +1} and `f̄ = 5 N`, computed only on non-neutral labels.
   - *Force-thresholded* (ManipTrans): `exp(−λ_c / Σ_f C_f · 1[d_human < ξ_c])`; HDMI: position term × `max(exp((‖F‖−F_thres)/σ_frc), 1)` — rewards sufficient-but-bounded force.
   - *Contact-time saturating* (GRAIL): `min(N_contact/N_min, 1)`.
   - *Object-frame vertex attraction with normal alignment* (DexMan): `(1 + γ⟨n_rob, d̂⟩)·exp(−λ‖p_rob − v_obj‖²)` — the `⟨n, d̂⟩` factor kills back-of-hand contacts.
   - *Contact graph* (PhysHOI/InterMimic): binary per-body contact indicators, `exp(−|c − ĉ|·w_cg)`, plus a contact-*energy* penalty `exp(−w·‖F‖²)` to discourage slamming.
   - *Contact wrench space* (CHORD, newest): compares the **support functions** of the human and robot contact-wrench matrices over `b` sampled 6-D directions, with tolerance β:
     `r_cws = exp(−‖max(0,(1−β)σ_h − σ_r)‖²/v − ‖max(0, σ_r − (1+β)σ_h)‖²/v)`, plus explicit penalties for unintended (`σ_h=0, σ_r>0`) and missed (`σ_h>0, σ_r=0`) contacts. Motivation: a position-matched contact can be *spatially* right but have a normal nearly perpendicular to the demo's, producing no useful wrench.
   - **Ablation numbers:** DexMan TACO 27.4→7.2% w/o contact; CHORD box-grab 0.702 (wrench) vs 0.334 (position-only, DexMachina-style) vs 0.384 (none); mixer-use 0.894 vs 0.624 vs 0.423. HDMI has both an interaction-reward and a contact-termination ablation. ManipTrans: contact in reward improves SR, contact as observation accelerates convergence, contact as termination is critical for final convergence.

3. **Fingertip-to-object distance.** Dexplore's `R_D = exp(−λ_D‖D̂ − D‖²)` over per-joint→nearest-surface-point vectors; GRAIL's `exp(−γ·mean‖f_j − c_t‖)`; DexMan's attraction term; Weave's fingertip-to-surface vectors as observations.

4. **Hand opposition / force closure.** InterPrior originates it (`e_h = 1 − mean_j (1 − u_Tᵀ u_j)/2`, `r_h = exp(−w_h e_h)`, `w_h` grows as distance shrinks); Weave adopts it verbatim at weight 2.0; GRAIL's `[−cos(d_thumb, d_index)]⁺` is the 2-finger version. Weave additionally uses a differentiable **force-closure quality** `Q̂_FC` at *retargeting* time (Ferrari-Canny style: `min_{‖w‖=1} max_{f∈F,‖f‖₁≤1} wᵀGf`), not in the RL reward. CHORD's reduced objective `r_fc = (1/B)Σ 1[σ_{r,b} > ε]` is *equivalent to force closure when maximized* — used when contact estimates are noisy.

5. **Behavior cloning to retargeted joints.** DexMachina `r_bc = (1/J)Σ exp(−β_bc‖q̂_i − q_i‖₂)` with **β_bc = 500** (very sharp) and λ_bc = 0.3. ManipTrans's `r_finger` over 21 keypoints is the keypoint-space equivalent; CHORD's `r_imit`; Weave's `motion_body_pos/ori`; TopoRetarget's joint term. Universally down-weighted relative to the object term — the explicit design intent in DexMachina is *"Because the auxiliary rewards use a much smaller weight, the policy can deviate from the reference hand motions learned at the earlier stages in order to prioritize optimizing for high task rewards."*

6. **Regularization.** Action rate L2 (−0.1 in Weave/HDMI), joint-limit L1 (−10.0 in both), foot slide (−1.0), foot air time (+0.5), joint power/energy (PhysHOI/InterMimic `eg1/eg2/eg3`, Dexplore's `R_energy`), second-order action smoothness (TopoRetarget `‖a_t − 2a_{t−1} + a_{t−2}‖²`).

### Virtual object force / decaying assistive force — who uses it and how they anneal

| System | Mechanism | Annealing schedule |
|---|---|---|
| **DexMachina** (originator) | 6 virtual 1-DoF base joints + 1 articulation joint on the object, all PD-actuated to the demo state; `F = k_p(p̂−p) − k_v v` | **Reward-gated exponential.** Decay `k_p ← k_p·φ_p` only when *all four* normalized rewards (task/imi/bc/con) exceed thresholds `σ = {0.5, 0.05, 0.05, 0.05}` averaged over a 100-episode deque. `k_p ≤ 0.01 → k_p = k_v = 0`. Alternatives in code: `fixed` (interval=500 epochs, first_ratio=0.3, first_stop=7000, second_stop=16000), `uniform` (sample gains from a shrinking interval, `upper_ratios kp=0.5 kv=0.9 fr=0.95`). Hard zero at 30,000 epochs. Dialback ×0.98 if episode length collapses below 50. Init `kp=1000, kv=10, force_range=50` (example script: 80 / 5). |
| **ResMimic** | Same idea, explicitly *"inspired by [41]"* = DexMachina. `F_t = k_p(p̂^o − p^o) − k_d v^o`, `T_t = k_p(θ̂^o ⊖ θ^o) − k_d ω^o` | Gains "gradually decayed". Qualitative ablation is the most informative bit: without VOC, *"the policy initially focuses only on motion tracking to reach the object, causing the object to be knocked over, which yields low object rewards and frequent early terminations. This quickly drives the policy into a local minimum where the robot retreats rather than engaging with the object."* |
| **CHORD** | Uses the DexMachina VOC directly (cites [49]) | *"we reset the simulator to arbitrary states along the reference trajectory and **keep the VOC fully active for a short stabilization window**, allowing the robot to recover contact before assistance is annealed"*, then anneals through a curriculum. |
| **ManipTrans** | *Not* a force on the object — instead relaxes **physics**: gravity G → 0, friction F → high, then restore | `gravity 9.81 → 0.005`, `friction 5.0 → 1.0`, exponential, interval 500 epochs, `rew_threshold task=0.6` in the auto mode. Coupled with ET-threshold annealing. |
| **REGRIND** | **Gravity curriculum** only: *"gradually increase the gravity magnitude from zero to its full value, which is useful for tasks involving picking up objects"*; plus a push-strength curriculum on both robot and object | not specified numerically |
| **FALCON** | Inverse direction — a **torque-limit-aware 3D force curriculum** that *escalates* the disturbance force on the end-effector `α_g: 0 → 1` | Progressive, respecting per-joint torque limits, with randomized force application position |
| **Dexplore** | No forces — instead anneals the **early-termination thresholds**: `κ = κ_init · N_fail/N_total` | Adaptive to the online failure rate, per-frame |

**Rule of thumb from the corpus:** decaying *assistive object forces* (DexMachina/ResMimic/CHORD) and relaxed *physics* (ManipTrans/REGRIND) are interchangeable in intent; the reward-gated schedule is strictly safer than a time-based one, because a time-based decay that outpaces learning collapses the policy into the "retreat" local minimum.

## (B) How whole-body balance interferes with manipulation tracking

**This is the best-evidenced claim in the survey. Five independent groups measured it.**

**1. GRAIL's `w/o π_φ` row is the cleanest single data point.** Vanilla SONIC (whole-body tracker, no object adaptor) achieves the *best* body tracking of all six variants (MPJPE-L **37.1 mm**) and the *worst* manipulation success (**39.7%**). Full GRAIL trades 4.7 mm of body accuracy (41.8 mm) for **+41.7 pp SR** and halved object error (0.303 → 0.135). Paper's words: *"accurate body imitation alone is insufficient for object interaction."* (https://arxiv.org/abs/2606.05160)

**2. ResMimic:** base GMT policy alone → **10% SR** vs ResMimic 92.5%, *"Although GMT alone yields slightly lower joint tracking error (due to its training objective), it performs poorly on object tracking and overall task completion."* Also documents the failure mode caused by the conflict: the policy learns to **retreat rather than engage** because approaching the object under a motion-tracking reward knocks it over, which triggers ET. (https://arxiv.org/abs/2510.05070)

**3. Weave** names the mechanism as a **gradient-scale** problem, not a reward-weight problem: *"the reward couples body tracking, object tracking, and finger contact, whose gradients differ substantially in scale: an update dominated by the body tracking term yields a policy that follows the reference pose without closing fingers, a local optimum that early training falls into easily."* Their fix is the optimizer (Muon's orthogonalized momentum) rather than tuning — and the optimizer contributed more than the architecture. (https://arxiv.org/abs/2609.16683)

**4. CoorDex** isolates the *action-space* half of the same problem. Under identical environment, reward, and PPO budget on a walking G1: All-Joint-Space → **0% success, 0% grasp** (and the policy "twists the whole body into unnatural postures to avoid falling"); Body-Prior + Hand-Joint-Space → **0% success, 1% grasp** (and it learns to **stop** near the object 90% of the time, converting loco-manipulation into stationary grasping). CoorDex → 55% success, 0% stop, 0% fall. Their explanation for why the base is fixed/stabilized in hand-prior training: *"A hand prior that must also explain 6D wrist motion spends much of its capacity on body-side placement rather than on finger control."* (https://arxiv.org/abs/2606.23680)

**5. InterMimic's own released G1 config is the ablation nobody labels as one.** Moving from the SMPL-X humanoid to the G1 29-DoF-with-hand embodiment, the authors set `op: 5.0 → 0.0` (world-frame object position reward *disabled*), `ig: 5 → 20` (interaction graph 4×), `r: 1.5 → 10` (body rotation 6.7×), `p: 30 → 10`. Combined with the fact that `compute_obj_reward` already expresses object pose in the humanoid's heading frame, the practical conclusion is: **on a real humanoid, do not reward world-frame object position; reward the relative hand-object geometry.**
(configs: https://github.com/Sirui-Xu/InterMimic/blob/main/isaacgym/src/intermimic/data/cfg/omomo_g1_29dof_with_hand.yaml vs `omomo_train_new.yaml`)

**Why so many works fix the base or use a floating wrist — stated reasons:**
- **ManipTrans / DexMachina / DexTrack / Dexplore** all add 6 virtual wrist DoF. DexTrack: *"We additionally add three translation joints and three revolute joints to control the global position and orientation of the hand."* Dexplore: *"the wrist is modeled as a floating root joint in world coordinates."* This removes the balance problem entirely and makes the wrist directly commandable, so **all** reward capacity goes to object + fingers.
- **ObjDex** keeps arms but mounts them as fixed-base UR10e, and explicitly says: *"Training RL policy that controls both robot arms and two multi-finger hands is possible in theory, but presents substantial challenges in practice due to the high degree of freedom of the robot action space."*
- **DexMan** keeps the real G1 but **freezes the lower body**: *"keeping the lower body fixed since tabletop tasks do not involve lower-body motion"* — and still beats floating-hand ManipTrans by 19 pp, which is the strongest evidence that *arm* kinematics aren't the problem; *balance* is.
- **Weave** frames the field split exactly this way: reference motion tracking *"supervises robot and object motion at the body and arm level and leaves finger-level hand-object contact unmodeled; dexterous interaction learning does model such contact, yet targets simulated characters or **fixed-base hands** whose kinematics and actuation differ from a humanoid with underactuated hands."*
- **CoorDex** on the prior literature: *"they often assume that the wrist or arm trajectory is provided by teleoperation, planning, a fixed-base setup, or a stationary whole-body controller. As a result, existing humanoid loco-manipulation systems are often simplified into a stop-and-go process."*

**Practical takeaway for a G1 + Dex3 object-tracking score:** if your challenge's episodes don't require locomotion, freeze or strongly regularize the lower body (DexMan's choice), express the object reward and observation in the robot root frame (InterMimic/HDMI/TopoRetarget/GRAIL), and if you must keep whole-body control, either factor the action space into priors (CoorDex/GRAIL) or fix the gradient scaling (Weave/Muon).

## (C) Decoupled upper/lower body control — when it helps and when it hurts

| System | arXiv | Decoupling | Verdict |
|---|---|---|---|
| **ExBody** | https://arxiv.org/abs/2402.16796 | **Asymmetric reward:** upper body imitates the reference motion; **legs are relieved of imitation** and only required to track a commanded root velocity robustly | Helps expressiveness+sim2real; the original "relax the legs" recipe |
| **ExBody2** | https://arxiv.org/abs/2412.13196 | *"decoupling the velocity tracking of the entire body from tracking body landmarks"*; teacher→student with automatic infeasible-motion filtering | Helps stability at the cost of exact global tracking |
| **HOMIE** | https://arxiv.org/abs/2502.13013 | Hard split: RL lower body mapped to a pedal, **isomorphic exoskeleton** for arms, gloves for hands. Upper-body **pose curriculum**, height-tracking reward, symmetry | Extreme decoupling; makes teleop tractable, forfeits coordination |
| **TWIST** | https://arxiv.org/abs/2505.02833 | Explicitly **against** decoupling — single whole-body controller from retargeted MoCap; RL+BC | *"most current humanoid teleoperation systems fall short of enabling coordinated whole-body behavior, typically limiting themselves to isolated locomotion or manipulation tasks."* ResMimic reuses TWIST's motion reward wholesale |
| **CLONE** | https://arxiv.org/abs/2506.08931 | **Against** decoupling, MoE + closed-loop error correction from head+hand MR tracking | *"current teleoperation systems… decouple upper- and lower-body control to maintain stability, restricting natural coordination, and operate open-loop without real-time position feedback, leading to accumulated drift"* → enables "picking up objects from the ground" |
| **FALCON** | https://arxiv.org/abs/2505.06776 · https://github.com/LeCAR-Lab/FALCON (MIT, 430★, L4DC 2026 Oral) | **Dual-agent RL**: lower-body agent = stable locomotion under external force; upper-body agent = EE position tracking with implicit adaptive force compensation; **jointly** trained | The best-quantified case *for* decoupling — see below |
| **SkillBlender** | https://arxiv.org/abs/2506.09366 | Pretrain goal-conditioned **task-agnostic primitive skills**, then blend | *"minimal task-specific reward engineering… naturally regularizing behaviors to avoid reward hacking"* |
| **JAEGER** | https://arxiv.org/abs/2505.06584 | Two independent upper/lower controllers; supports root-velocity (coarse) and joint-angle (fine) tracking | *"This separation alleviates the dimensionality curse and improves fault tolerance"* |
| **OpenHLM** | https://arxiv.org/abs/2606.22174 | **Against** decoupling | *"most existing systems typically decouple the upper and lower bodies into separate controllers, limiting such coordination and yielding behaviors similar to those of a wheeled dual-arm platform."* Finds a **joint-based whole-body teleop interface outperforms alternatives that only partially expose the DoFs** |
| **SMASH** (ping-pong) | https://arxiv.org/abs/2604.01158 | Against | *"we achieve agile and precise ball interaction with tightly coordinated whole-body control, rather than relying on decoupled upper- and lower-body behaviors"* |

**FALCON's numbers (the load-bearing evidence).** Unitree G1 in IsaacGym, 252 ACCAD motion targets, three force levels on both end-effectors. Upper-body joint tracking error / root velocity tracking error:

| method | No-Force | Mid-Force | **Large-Force** | root (No/Mid/Large) |
|---|---|---|---|---|
| Monolithic-WB-RL, no force curr. | 0.46 | 1.03 | 1.65 | 0.34 / 0.67 / 1.28 |
| Monolithic-WB-RL, with force curr. | 0.43 | 0.50 | 0.73 | 0.28 / 0.32 / 0.44 |
| FALCON, no force curr. | **0.14** | 0.55 | 1.06 | 0.32 / 0.66 / 1.24 |
| **FALCON, with force curr.** | 0.21 | **0.24** | **0.37** | 0.27 / 0.30 / 0.45 |

FALCON's diagnosis of *both* competing paradigms: *"Lower-RL-Upper-IK approaches suffer from delayed force compensation for upper-body control. Monolithic-Whole-body-RL methods face sample inefficiency from coarsely related task objectives between upper-body manipulation and lower-body [locomotion]."* Real-world envelope: payloads 0–20 N, cart pulling 0–100 N, door opening 0–40 N, transferred across multiple humanoids **without embodiment-specific reward or curriculum tuning**.

**The reconciliation.** Every "decoupling hurts" paper (TWIST, CLONE, OpenHLM, SMASH) is about **teleoperation/data-collection interfaces and whole-body expressiveness**, where a decoupled interface truncates the reachable behavior set. Every "decoupling helps" paper (FALCON, JAEGER, SkillBlender, CoorDex, GRAIL, ResMimic) decouples in **learning structure** — separate agents, latent priors, or residual layers — while still training jointly in one environment and keeping the physics coupled. CoorDex is the sharpest statement of the second position: decoupling into *frozen latent priors* with a *shared coordination trunk* and *separate residual heads* is what makes finger-level contact learnable at all on a walking humanoid; decoupling into *separate joint-space controllers* would not have been.

**Carrying loads:** FALCON (implicit force compensation + torque-limit-aware curriculum) and ResMimic (contact reward pushing torso+arm contact instead of wrist-only) are the two relevant recipes. ResMimic's contact-reward ablation is instructive: without it, the policy lifts a box with wrists/hands alone — which succeeds in IsaacGym and **fails in MuJoCo and reality**; with it, the policy uses coordinated torso+arm contact and carries **4.5 kg on a G1 whose wrist payload limit is ~2.5 kg**.

## 3. Concrete recommendations for a G1 + Dex3 / Isaac Lab / ADD-AUC entry

1. **Start from Weave's Isaac Lab env** (https://github.com/xiaohu-art/Weave) and swap `G1-Inspire-HOI-v0` for a Dex3 variant. It is the only public repo with the exact stack (Isaac Lab + rsl_rl + G1 whole-body + finger DoF + object-pose reward + object-error terminations), and it is being pushed to daily. Its `configs/track/train.yaml` is a working set of weights you can start from without guessing. Note: no LICENSE file — check with the authors before building on it commercially.
2. **Lift DexMachina's `dex3_hand` assets** (`dexmachina/assets/dex3_hand/dex3_{left,right}_6dof.urdf`, MIT) if you need a floating-wrist Dex3 for a pretraining stage, and `dexmachina/envs/hand_cfgs/dex3.py` for the actuator gains (finger kp=100/kv=6, wrist_rot kp=200/kv=10, wrist_trans kp=300/kv=5, force_range 50) and the collision-group layout.
3. **Score-aligned reward:** since you're scored on ADD-AUC, use DexMachina's exact metric definition (per-part ADD, averaged, then AUC — *not* ADD-S) and consider ResMimic's point-cloud object reward, which is the reward that most directly matches an ADD-style metric (`exp(−λ Σ_i ‖P[i] − P̂[i]‖₂)`) rather than a decoupled pos+rot pair.
4. **Put the object observation and reward in the robot root frame.** GRAIL paid 23.5 pp SR for not doing it; InterMimic's own G1 config disables world-frame object position entirely.
5. **Use a VOC with reward-gated annealing** (DexMachina `curriculum.py` is MIT and directly copyable) rather than a time-based decay — it is what prevents the "retreat instead of engage" collapse ResMimic documents.
6. **Budget two contact terms, not one:** a contact-*matching* term (Weave's force-normalized ternary version is the cheapest) plus a hand-*opposition* term (InterPrior's `u_Tᵀu_j`, distance-modulated). For a 3-finger Dex3 the opposition term degenerates gracefully to thumb-vs-{index, middle}, which is exactly GRAIL's 2-finger form.
7. **Freeze/regularize the lower body** unless locomotion is scored. If it is, factor the action space (CoorDex latent priors, GRAIL latent adaptor, ResMimic residual-on-GMT) rather than training joint-space whole-body PPO — the measured outcome of the latter on a walking G1 grasp task is 0%.
8. **Watch the gradient scale.** If you keep a monolithic policy, Weave's Muon+SimBaV2 result is the cheapest available fix for the body-dominates-fingers local minimum, and it's already wired into their repo.
