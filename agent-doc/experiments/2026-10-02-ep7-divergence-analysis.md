## 2. 机制（读代码，`results/ep7/code_facts.txt`）

训练挂的是 v0.4.0 加 #185 补丁；#185 只改 `scene/support.py`，下面几处与 v0.4.0 相同。

1. **一个 NaN 奖励就让奖励归一化器永久失效。** 采集一步时，先用这一步每个世界的奖励更新归一化器，再写回放缓冲（`learner.py:1060–1081`）。
   归一化器里每个世界的折扣回报是 `discount * (~done) * 上一步 + reward`，全局量取 `jnp.max(jnp.abs(...))` 与 `jnp.mean`、`jnp.var`（`reward_normalization.py:63–64, 101–106`），
   文件里没有任何非有限过滤。一个世界一步的 NaN 奖励就让全局的最大绝对回报与滑动矩变成 NaN；那个世界自己的折扣回报在回合结束后也回不来（0 × NaN 仍是 NaN）。
   之后所有批次的归一化奖励都是 NaN，critic 的梯度非有限、更新全部跳过，loss scale 每次减半直到 0。W&B 里 `reward_normalization/scale_denominator` 从事件那一行起是 nan，
   critic 跳过比例随即到 1，与此吻合。
2. **BatchNorm 滑动统计同样不设防**（9/30 的 C4）：批次里有非有限的观测，统计量就永久变 NaN，之后 actor 对所有世界输出 NaN。更新是每采集一步 4 次（G1 配方 `g1_recon_body_flash_sac.yaml:53` 把基础配置的 2.0 改成 4.0）、批大小 2048、n-step 7（`reference_flash_sac.yaml:63`、`g1_recon_body_flash_sac.yaml:74`）。
3. **训练端不检测非有限的世界。** ReconBody 的终止判定只把误差与阈值比大小（`termination.py:603–604, 640–646`），位置误差是 NaN 时这个比较不成立；
   `envs/`、`lifecycle/reset.py`、`objectives/recon_body.py` 里没有非有限检测。评测端有：`evaluation/rollout.py:276–280` 会找出记录了非有限位姿的世界并排除，说明上游知道仿真会出非有限状态。

按这些代码读 W&B 的记录：某个世界的仿真状态先变成非有限（当时动作还是有限的）→ 这一步的奖励是 NaN → 奖励归一化器永久 NaN、critic 停止更新 → 带非有限观测的样本被抽进批次 → BatchNorm 统计量 NaN → 所有世界的动作 NaN。
t1-ep7 从事件到全面崩掉隔了两行，t2-ep7 隔了一行。

## 3. 判断

已核实（脚本输出或代码原文，jev 见第 6 节）：
- 两条 ep7 run 的第一行非有限记录分别在 132,710,400 步（VOC 0.25）与 142,796,800 步（VOC 0.1），之前训练正常。
- t2-ep7 里先变 nan 的是骨盆位置误差与位置类奖励，同一行动作仍有限，所以第一个非有限值来自环境（仿真状态），不是来自优化器。
- 奖励归一化器、BatchNorm 统计量、终止判定、回放写入都没有非有限过滤；一个 NaN 奖励足以让 critic 永久停止更新。

推断（没有直接证据）：
- **触发是某一个世界的仿真数值崩掉。** 关节、物体、手掌、骨盆四个位置类奖励同时是 nan，更像整个世界（机器人连同物体）一起变成非有限，而不是某一个奖励函数的数值问题。
- **与 ep7 的场景有关，且在辅助力变小之后才出现。** ep7 的桌面是 30 条里最薄的支撑面：0.84 × 0.282 × 0.01 m 的方盒（半高 5 mm）；11 条序列的 12 个圆柱支撑面都是 4 cm 厚，ep1、ep28 的方盒最薄的一边是 2 cm（`results/diverge/support_shapes.txt`）。
  任务是手按着熨斗在桌面上来回滑。VOC 降到 0.25 以下后，物体要靠手与桌面的真实接触来带动；薄板上的持续滑动接触在某个世界里穿透过深、求解发散，是一个说得通的解释，没有验证。
- **那个非有限的世界可能没有被及时清掉。** t1-ep7 第 2592 行其余世界仍正常（回合长度 410、没有骨盆终止），但这一行骨盆位置误差仍是 nan（日志累加量每个窗口清零，说明这一行的窗口里仍有世界给出 NaN 的骨盆误差），吞吐从约 50,300 步/秒降到 24,816 步/秒。这些与“坏世界没被清掉”相容，但不是直接证据：同一行动作均值也是 nan，也可能是 actor 的 BatchNorm 已经坏了、动作本身变成 NaN。
  终止判定对 NaN 的行为取决于 Warp 对 NaN 四元数的归一化与比较，没有实测。

不知道：
- 崩在参考的哪一帧、哪一组接触上。行级记录分辨不出，本地也没有留下事件之前的回放数据（回放缓冲不随 state 保存，`save_replay: false`）。
- VOC 为 0 时这种事件有多频繁。评测与提交都在 VOC 为 0 下跑。
- 两份最后有限的 policy（t1 的 130,004,992 步、t2 的 140,005,376 步）在 VOC 为 0 下的质量。它们分别只训到 VOC 0.25、刚进 0.1。
