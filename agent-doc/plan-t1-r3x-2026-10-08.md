## 3. 做法

1. **代码**（各带测试）：
   - `stages/policy/make_r3x_queue.py`：从 ml40 基线的期望表与队列行派生上面 6 条（复用 `make_trial_queue.py` 的 `baseline()` 核对），写
     `stages/policy/queues/mf4090_r3x{.expect.tsv,_smoke.txt,.txt}` 与导出清单 `stages/evaluate/exports/cand_t1_r3x_mf4090.tsv`；测试 `test_make_r3x_queue.py`。
   - `stages/evaluate/export_after_eval.sh`：导出门。评测链最后一行是“成功 N、失败 0”才跑导出链；否则一条都不导，写 `runs/logs/<导出名>_gate.log`，
     最后一行 `EXPORT_GATE_STOPPED`；测试 `test_export_after_eval.py`。
   - `stages/policy/arm_r3x_chain.sh`：起链前核对（GPU 是 4090、来历干净、日志与会话不存在、GPU 空、可用 ≥ 4000 MB、副本按清单核对、`v2d_meta.json` 都在、
     run 目录里没有训练产物、导出清单与期望表一致、12 份配置 precheck 与配方断言），再起三个会话：训练链 → 评测链（等训练链结束，只评最终 checkpoint，
     4096 世界）→ 导出门（等评测链结束，干净才导出，1 个世界，`V2D_FALLBACK_MAX=0`）。`V2D_ARM_DRYRUN=1` 只核不起。
   - `stages/evaluate/select_t1.sh`：输出名与输入目录改由 `V2D_SELECT_TAG`、`V2D_SELECT_DIR` 指定（不设时是 10/8 的行为）；同一标签的分数文件已存在就拒绝。

## 4. 判据（执行前登记）

| 编号 | 判据 |
|---|---|
| R1 训练健康 | 每条 run：冒烟通过，有 `DONE`，没有 `NONFINITE`（最终 policy 有限），run 日志里 `NONFINITE_GUARD_STOP` 0 次；训练链最后一行的“发散”为 0 |

| R3 导出 | 每条导出状态 `ok`（只用最终 checkpoint，不回退） |
| R4 选择门 | `select_t1.py` 的 A 门（≤ 1e-9）、B 门（≤ 1e-4）都过；`select_t1_compare.py` 的 C1–C5 都过 |

`select_t1_compare.py` 的五项：C1 10/8 的 48 个候选分数不变（≤ 1e-9）；C2 新出现的候选都在导出清单里；C3 其余 27 条 episode 选中的 run 不变；
C4 ep0、ep5、ep15 选中的是原来那条或这条 episode 的新候选，且按登记规则不比原来差；C5 打包合计等于 30 条选中者的平均（≤ 1e-6）。

- R1–R3 不过的 run 不进候选，照实记下，不换参数重跑。原因在基础设施（W&B 网络、GPU 被占、磁盘）时，可以用同一配置原样重跑一次，记下。
- **评测链没有干净结束时**（例如开头见到 GPU 上有别的进程而失败）：导出门不导出任何一条。先补评（换一个日志名，起评测链、不设 `V2D_WAIT_FOR_LOG`，
  同一期望表、`V2D_EVAL_STEPS=349999104`），评测链以“失败 0”结束后，用同一个导出名手动起导出链（`V2D_FALLBACK_MAX=0`）。补评不算重新抽样：
  交上去的是 1 世界导出，它在这条路径上仍然每个 checkpoint 只做一次。
- R4 任一项不过：不用这一次的 CSV，停下查原因。
- 选择规则沿用 10/8 登记的那一套，不改；每个 checkpoint 只导出一次，不为“抽”更好的一次重导。
- **只报**：ep0、ep5、ep15 各候选的四项分数与 4096 世界 MP-SR、换没换；新 CSV 与 10/8 CSV 的合计对比；6 条 run 的 4096 世界指标与对应基线并列，
  注明 buffer、机器、训练副本、配方同时变了，不作为变体 A 的证据；防护事件 `NONFINITE_GUARD` 的行数。

## 5. 风险

- **摔倒**：变体 A 已知会让摔的比例升高。逐条选只在交上去的那条轨迹更好时才换，摔了的那次不会进 CSV。
- **抽签**：候选越多，交上去的分数越多地反映挑选。报告里把选中者的 4096 世界 MP-SR 并列，区分实力与运气。
- **GPU 被占**（mf4090）：同组容器若开始用 GPU，训练链在下一条 run 前停下；评测链开头见到别的进程就以失败结束，导出门随之不导出（补救见第 4 节）；
  导出链本身遇到 GPU 被占最多等 2 小时。停了就报告并问用户，不动别人的容器。
- **ml40 上同事的任务**：打分不用 GPU，但同事的任务可能占满 CPU、内存或 `/lab_data`（docker 的根目录在那里，满了容器起不来）。打分前先看一眼（第 3 节第 5.3 步）；
  慢一些不影响结果。同步 ml40 只改我们自己的仓库目录。
- **磁盘**：6 条约 2–2.5 GB，起链时可用 ≥ 4000 MB；训练链在不到 1200 MB 时停。
- **链被意外杀掉**（`kill -9`、机器重启）：没有结束行，下游的链会一直等，长链标记留着挡同步。先确认三个 tmux 会话与相关进程都不在，再删 `runs/.chain-active-r3x_*`
  与 `runs/.chain-active-cand_t1_r3x_mf4090*`，按第 4 节从断处续。
- **Mac 离线**：链在 mf4090 的 tmux 里跑，不受影响；第 5 步要等 Mac 在线。
- **档位隔离**：只碰 Tier 1。
